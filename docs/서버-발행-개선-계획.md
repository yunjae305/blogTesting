# 서버 발행 개선 계획 (채택 2026-08-18)

브라우저(발행 크롬)를 **서버에 그대로 두고**, 서버 발행이 깨뜨리던 문제를 각개로
푼다. 발행 에이전트(사용자 PC 발행, [발행-에이전트-설계.md](발행-에이전트-설계.md))는
이 방향 확정으로 2026-08-18에 **코드째 제거**했다(복구 경로는 설계 문서 머리말 참고).

목표: **사용자 약 10명이 외부 PC에서 동시에, 각자 자기 계정으로** 발행할 수 있다.

## 작업 목록과 구현 상태

2026-08-18에 A·B·C·D·병렬화 전부 **코드 구현 완료**(테스트 포함). 실발행 검증과
B-0 실험은 사람이 해야 한다(아래 '남은 일').

### 작업 A — 클립보드 잠금 + 붙여넣기 직전 대조 (구현 완료, 기본 켜짐)

OS 클립보드는 기기 전체에 하나다. 발행 두 건이 겹치면 쓰기→Ctrl+V 사이에 서로를
덮어써 **다른 사람의 글이 붙는다.**

- `posting/naver/clipboard.py` — `use_os_clipboard()`(프로세스 전역 재진입 잠금,
  쓰기→붙여넣기→DOM 반영 확인까지 한 덩어리), `clipboard_still_holds()`(쓴 바이트의
  SHA-256 지문을 붙여넣기 직전에 실제 클립보드와 대조).
- `posting/naver/editor.py` — 제목·스캐폴드·이미지·캡션 4개 붙여넣기 지점이 잠금
  구간 안에서 `_paste_verified()`를 거친다. 대조가 어긋나면 **붙여넣지 않고**
  (fail-closed) 클립보드에 다시 넣어 재시도, 소진되면 발행 중단.
- 잠금이 못 막는 것(다른 프로세스: 서버에서 사람이 복사, 원격 데스크톱 동기화)을
  대조가 잡는다. 남는 창은 'Ctrl+V 키가 에디터에 닿기까지의 수십 ms'뿐이고, 그것은
  B가 없앤다.
- 테스트: `tests/test_clipboard_isolation.py`. 실기기 왕복 검증(쓰기→대조→끼어듦
  감지) 2026-08-18 통과.
- 대가: 발행끼리 붙여넣기 구간이 직렬화된다(문단 단위 몇 초씩). 10명 동시 발행이
  본격화되면 B로 없앤다.

### 작업 B-0 — 합성 붙여넣기 실험 (스크립트 완료, **실행은 사람**)

SmartEditor가 isTrusted=false인 합성 paste 이벤트(특히 이미지 File)를 받는지는
실험으로만 알 수 있다.

    python apps/api/scripts/probe_synthetic_paste.py

실제 발행 경로 전체(제목→스캐폴드→이미지→캡션→검증)를 합성 모드로 태운다. 발행
버튼은 누르지 않는다. 먼저 `python apps/api/scripts/naver_login.py`로 세션을 저장.

### 작업 B — 합성 DataTransfer 붙여넣기 (구현 완료, **2026-08-19부터 기본**)

OS 클립보드를 아예 쓰지 않는 발행. 페이지 안에서 `ClipboardEvent('paste')`를 만들어
쏘므로 발행끼리 완전히 독립이고(잠금 불필요), 사용자의 복사와도 겹치지 않는다.
**10명 동시 발행의 전제다.**

- **기본 모드는 `auto`다.** 값은 셋: `auto`(기본 — 합성을 먼저 시도하고, 거부되면
  **그 발행 인스턴스만** 클립보드 경로로 갈아탐) · `synthetic`(엄격 — 클립보드를 절대
  안 씀) · `clipboard`(항상 기존 경로 — A의 잠금+대조).
- **2026-08-19 실발행 결과: 스마트에디터 ONE은 합성 paste를 받지 않는다.** 제목은 키
  입력 폴백으로 들어갔지만 본문 스캐폴드에서 즉시 실패했다(`synthetic` 기본으로
  잠깐 뒀다가 발행이 막혔다). 그래서 기본을 `auto`로 되돌렸다 — 합성이 통하게 되는
  날 자동으로 무잠금 병렬이 되고, 그때까지는 클립보드 경로로 안전하게 돈다.
- 에디터가 이벤트를 소비하지 않을 때(fail-closed): **제목**은 신뢰 키 입력(실제
  타이핑)으로 폴백, **이미지**는 업로드 자동화(파일 입력에 직접 첨부, OS 대화상자를
  띄우는 버튼 클릭은 안 함)로 폴백, **본문 스캐폴드**는 대체 수단이 없어 명확한
  오류로 멈춘다(서식·구조가 통째로 사라지는 키 입력 대체는 하지 않는다). 어떤
  폴백이든 기존 DOM 검증(제목 대조·스캐폴드 상태·이미지 수·발행 전 앞뒤 텍스트
  대조)은 그대로 지나야 한다.
- 진행 상황은 `[NAVER_PUBLISH]` 로그로 남는다: `mode=` · `title_input=` ·
  `body_paste=` · `image_paste=` · `image_upload=` · `verify=` · `publish=`.
- 테스트: `tests/test_synthetic_paste.py`(모드·폴백·격리),
  `tests/test_clipboard_isolation.py`(clipboard·auto 전환 후 경로).

### 작업 C — 라이브 뷰: 크롬 화면 중계 + 원격 조작 (구현 완료)

**원래 문제의 해법이다**: 외부 PC 사용자는 서버에 뜬 크롬(로그인·2단계 인증·캡차)을
볼 방법이 없었다. CDP로 푼다 — `Page.startScreencast`(JPEG 프레임, 창이 가려져
있거나 RDP가 잠겨 있어도 렌더러에서 나온다) + `Input.dispatch*`(클릭·키보드).

- `posting/live_view.py` — 세션마다 **별도 CDP 웹소켓**(websocket-client, 동기)으로
  브라우저 레벨에 붙는다. WebDriver 세션은 건드리지 않는다(발행 스레드가 독점).
  새 탭 생성·파괴를 따라가고, 프레임은 **구독자가 있을 때만** 받는다.
- 라우트: `GET /live/sessions`(목록) · `GET /live/{channel}/stream`(SSE, fetch
  스트리밍으로 읽는다 — EventSource는 인증 헤더를 못 싣는다) ·
  `POST /live/{channel}/input`(0~1 정규화 좌표, 텍스트는 insertText — 한글 지원).
- 등록 지점(사용자 단위, 채널 naver·threads): 네이버 발행·로그인·미리보기, 스레드
  발행·로그인. **설정 화면의 로그인 경로에도 연결돼 있다** — 원래 문제였던 원격
  로그인이 이걸로 풀린다. 브라우저를 닫으면(close_browser) 세션도 내려간다.
- 프런트: `LiveBrowserView`(화면+클릭+키보드+한글 입력칸, 3초 재접속) ·
  `LiveSessionsPanel`(4초 폴링, 중계가 생기면 저절로 나타남). 발행 화면(StepPublish),
  예약 화면(ScheduledView), 설정의 네이버·스레드 로그인 카드에 붙어 있다.
- 기존 2단계 인증 코드 입력창(VerificationCodeModal)은 **그대로 둔다** — 코드형
  인증은 모달로, 그 밖의 모든 화면(캡차·승인·낯선 화면)은 라이브 뷰로. 라이브 뷰가
  실사용에서 검증된 뒤에 정리를 논한다.
- 테스트: `tests/test_live_view.py`, `apps/web/src/api/live.test.ts`,
  `LiveSessionsPanel.test.tsx`.

### 작업 D — 열어 둔 크롬 정리 (구현 완료)

발행 뒤 확인용으로 열어 둔 크롬은 '그 프로필의 다음 발행'만 닫아 줬다 — 사용자
10명이 한 번씩 발행하고 떠나면 크롬 10대(각 수백 MB)가 영원히 남는다.

- `posting/browser_reaper.py` — 열어 둔 지 `KEEP_OPEN_BROWSER_TTL_MINUTES`(기본
  15분)를 넘긴 창을 백그라운드 리퍼가 닫는다. **라이브 뷰로 보고 있는 창은 닫지
  않는다**(인증을 끝내는 중일 수 있다 — 보는 동안 수명이 미뤄진다). 0 이하로 두면
  예전 동작 그대로다.
- 테스트: `tests/test_browser_reaper.py`.

### 예약 발행 사용자별 병렬화 (구현 완료)

예약 워커의 발행 자리가 서버 전체에 하나뿐이어서(`_publishing` 단일 슬롯) 10명의
발행이 전부 줄을 섰다. 크롬 프로필은 사용자별이므로 서로 막을 이유가 없다.

- `modules/scheduled_posting/worker.py` — 발행 슬롯을 `user_id → task` dict로.
  같은 사용자는 여전히 하나씩, 다른 사용자는 동시에. 서버 전체 동시 크롬 수는
  `SCHEDULED_MAX_CONCURRENT_PUBLISH`(기본 10)로 막는다 — RAM 32GB 미만이면 줄인다.
- 테스트: `tests/test_scheduled_parallel_publish.py`.

## 환경 변수 정리

| 변수 | 기본 | 뜻 |
| --- | --- | --- |
| `NAVER_PASTE_MODE` | `synthetic` | `auto` = 거부 시 그 발행만 클립보드 전환 · `clipboard` = 항상 기존 경로 |
| `KEEP_OPEN_BROWSER_TTL_MINUTES` | `15` | 열어 둔 크롬 정리 시한, 0 이하 = 끄기 |
| `SCHEDULED_MAX_CONCURRENT_PUBLISH` | `10` | 서버 전체 동시 발행 크롬 상한 |

## 운영(nginx) 주의

- 라이브 뷰 SSE(`/live/{channel}/stream`)는 응답에 `X-Accel-Buffering: no`를 실어
  nginx 버퍼링을 응답 단위로 끈다 — 별도 설정 없이 동작해야 한다. 만약 프레임이
  뭉쳐서 온다면 해당 location에 `proxy_buffering off;`를 명시한다.
- 서버는 15초마다 keepalive 주석을 내보내므로 `proxy_read_timeout` 기본 60초에
  걸리지 않는다. 타임아웃을 따로 줄였다면 20초 이상은 남겨 둔다.
- 새 의존성: `websocket-client`(requirements.txt). 서버에서
  `pip install -r apps/api/requirements.txt` 한 번 다시 돈다.

## 남은 일 (사람)

1. **B-0 실험**: `probe_synthetic_paste.py`(전체)·`probe_synthetic_image_paste.py`
   (이미지만)를 서버(또는 세션 있는 PC)에서 실행. 기본이 이미 synthetic이므로 통과하면
   그대로 두고, **실패하면** 운영 `.env`에 `NAVER_PASTE_MODE=auto`(권장) 또는
   `clipboard`를 넣는다. 격리·병렬성만 따로 보려면 `probe_parallel_publish.py`
   (네이버 계정 불필요).
2. **라이브 뷰 실발행 검증**: 외부 PC에서 설정→네이버/스레드 로그인을 눌러 화면이
   중계되는지, 클릭·코드 입력이 통하는지. 발행 중 화면도 확인.
3. 서버 PC 로컬 Mongo에 `agent_devices`·`agent_jobs`가 있으면 지운다(Atlas는
   2026-08-18에 지웠다 — init_mongo는 이제 server 모드에서 안 만든다).
4. 서버 RAM 확인: 동시 10명이면 32GB 권장, 아니면
   `SCHEDULED_MAX_CONCURRENT_PUBLISH`를 낮춘다.
