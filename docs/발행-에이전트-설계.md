## 1. 배경 — 지금 무엇이 깨져 있나

발행은 셀레니움이 **서버 PC의 데스크톱에 크롬을 띄워** 네이버 스마트에디터와
threads.com을 사람처럼 조작하는 방식이다. 네이버가 2020년, 티스토리가 2024년에
글쓰기 API를 닫았기 때문에 다른 방법이 없다(`posting/publisher.py` 모듈 독스트링).

사용자가 몇 명이든 **크롬 창은 전부 서버 화면 하나에 뜬다.** 여기서 네 가지가 깨진다.

### 1-1. 클립보드가 섞인다 — 가장 심각하다

네이버 발행은 본문과 이미지를 **Windows 전역 클립보드**로 붙여넣는다.
`posting/naver/clipboard.py:105-124`가 `OpenClipboard` → `EmptyClipboard` →
`SetClipboardData`를 직접 호출한다.

```
사용자 A: 본문을 클립보드에 올림 ──┐
사용자 B: 본문을 클립보드에 올림 ──┤ ← A 것을 덮어씀
사용자 A: Ctrl+V ─────────────────┘ ← B의 본문이 A의 글에 들어간다
```

**클립보드는 PC에 하나뿐이다.** 크롬을 몇 개 띄우든 상관없다. 그리고 이 사고는
**실패하지 않는다** — 발행은 성공한 것처럼 끝나고, 남의 본문이 섞인 글이 올라간다.
로그에도 아무 흔적이 없다. 발견하려면 사람이 올라간 글을 읽어 봐야 한다.

수동 발행에는 이것을 막는 잠금이 **없다**. `blog_task/service.py:507`이 곧장
`_run_posting_worker`를 부르고, `posting/naver/browser.py:150`의 `_in_browser_thread`가
호출마다 데몬 스레드를 새로 띄운다. 개수 제한도 큐도 없다.

### 1-2. 2단계 인증·캡차를 서버 앞에 앉아야만 처리할 수 있다

크롬 창이 서버 화면에 뜨므로, 외부 PC에서 로그인을 눌러도 인증을 끝낼 사람이 없다.
발행 도중 2단계 인증이 걸리면 그 발행이 멈춘다.

발행 경로에는 앱 화면으로 코드를 물어보는 창구가 있다(`threads_browser.py:519-522`의
`_solve_verification`). 그러나 **설정 화면의 로그인 버튼에서는 켜지지 않는다** —
`threads_browser.py:281`이 `_ensure_logged_in`을 부르며 `user_id`를 넘기지 않아
`user_id: str = ""` 기본값으로 떨어지고, 코드 창구 대신 서버 화면 앞의 사람을 기다린다.

### 1-3. 사용자끼리 발행이 직렬화된다

예약 발행 자리는 `scheduled_posting/worker.py:191-192`의 `self._publishing` 하나뿐이고,
**서버 전체에 하나**다. 사용자 A의 발행이 도는 동안 사용자 B의 예약은 시각이 지나도
시작하지 않는다.

### 1-4. 크롬 프로필 잠금

같은 프로필로 크롬이 두 번 뜨면 `user data directory is already in use`로 실패한다
(`posting/naver/browser.py:447-451`). 서버를 재시작해도 크롬은 함께 죽지 않아
(`browser.py:159-161`) 유령 프로세스가 프로필을 물고 남는다.

## 2. 결정

**발행을 사용자 PC의 에이전트 프로그램으로 옮긴다. 예약 발행도 포함한다.**

원고 생성(LLM 호출)은 서버에 그대로 둔다.

```
                    서버 (변경 없음: 원고 생성 · Mongo · 비용 상한 · 예약 스케줄)
                              │
                    작업 큐  ─┼─────────────┐
                              ↓             ↓
                        A의 PC 에이전트   B의 PC 에이전트
                              ↓             ↓
                          크롬(A)        크롬(B)
                       클립보드·화면    클립보드·화면
                              └── 각자의 기계, 섞일 물건이 없다 ──┘
```

### 왜 이것인가

| 문제 | 해결되는 방식 |
|---|---|
| 클립보드 섞임 (1-1) | 클립보드가 기계마다 하나씩. **구조적으로 불가능해진다** |
| 2단계 인증 (1-2) | 크롬이 사용자 화면에 뜨므로 본인이 직접 처리 |
| 사용자 간 직렬화 (1-3) | PC가 다르므로 완전 병렬 |
| 프로필 잠금 (1-4) | 에이전트가 그 PC의 유일한 발행 통로 = 단일 큐 |
| 수동 vs 예약 충돌 | 같은 큐를 지나므로 자연히 직렬화 |

**수동/예약 직렬화는 따로 만들지 않는다.** 에이전트가 한 번에 하나씩 처리하면
그것이 곧 직렬화다. 지금처럼 예약 워커만 조심하고 수동은 뚫려 있는 상태가 아니게 된다.

### 검토했으나 택하지 않은 것

**noVNC로 서버 화면을 브라우저에 띄우기.** 코드를 거의 안 고치고 며칠에 끝난다.
2단계 인증만 원격에서 처리하면 되는 상황이면 이게 맞다. 그러나 **클립보드 문제(1-1)를
전혀 해결하지 못한다** — 화면이 하나라 두 명이 동시에 쓸 수 없다는 한계가 그대로다.
사용자가 둘 이상이라는 전제에서 탈락.

**크롬 확장 프로그램.** 사용자가 이미 네이버·스레드에 로그인해 있으므로 로그인·세션·
프로필 잠금 문제가 통째로 사라진다. 운영 난이도가 가장 낮다. 그러나 셀레니움 코드를
**전부 content script로 다시 짜야 한다** — `naver/editor.py`(1400줄 이상)에 쌓인
선택자 폴백·붙여넣기 타이밍·앵커 검증을 처음부터 다시 만드는 일이다. 재작성 비용이
가장 크다. 나중에 다시 검토할 값어치는 있다.

**Electron/Tauri 데스크톱 앱으로 전체 전환.** 서버를 없애면 API 키가 사용자 PC로
배포되고(`ANTHROPIC_API_KEY`·`OPENAI_API_KEY`), 전체 비용 상한(`COST_MAX_DAILY_USD_TOTAL`)이
무의미해지며, 팀 공용 암호화 키(`EMAIL_ENC_KEY`)와 공용 DB 전제가 무너진다.
서버를 남기면 그것은 **이 결정(에이전트)에 화면 껍데기를 씌운 것**과 같다.

그리고 Electron 내장 `BrowserWindow`로 셀레니움을 대체할 수도 없다. 지금 코드는
자동화 탐지를 피하려고 `undetected-chromedriver`를 쓴다(`naver/browser.py:438`).
내장 브라우저로 갈아타면 그 대응을 잃는다. 결국 파이썬 에이전트를 sidecar로 넣게 되므로
**에이전트가 먼저다.** 껍데기는 나중에 얹을 수 있고, 그때 버리는 작업이 없다.

## 3. 받아들이는 대가

### 3-1. 사용자 PC가 꺼져 있으면 예약이 안 나간다

지금은 서버가 항상 켜져 있어 없던 문제다. **이것이 이 결정의 가장 큰 비용이다.**

**결정: 유예 후 지연 발행.** 예약 시각에 처리 가능한 에이전트가 없으면 기다렸다가,
붙는 즉시 발행한다. 유예(기본 2시간)를 넘기면 `NEEDS_HUMAN`으로 넘긴다.

- `FAILED`가 아니라 `NEEDS_HUMAN`인 이유: 원고는 멀쩡하고 사람이 PC를 켜기만 하면
  올라간다. 실패로 표시하면 사용자가 원고를 다시 만들려 든다.
- 즉시 실패로 하지 않는 이유: 노트북을 덮어 뒀다고 완성된 글이 날아가면 안 된다.

### 3-2. 예약 시각에 크롬이 사용자 화면에 뜬다

오후 3시 예약이면 오후 3시에 크롬 창이 열린다. 회의 중이면 방해가 된다.

**결정: 창은 띄우되 앞으로 올리지 않는다.** `posting/naver/browser.py:468`의
`bring_to_front(driver)`를 예약 발행 경로에서는 호출하지 않는다. 트레이 알림으로
"발행을 시작했습니다"만 알린다.

**단, 2단계 인증·캡차를 만나면 그때는 앞으로 올리고 알림을 띄운다.** 그때는 사람이
필요하므로 방해하는 것이 맞다.

수동 발행(사용자가 직접 버튼을 누른 경우)은 지금처럼 앞으로 올린다 — 본인이 방금
누른 것이라 창이 보이는 게 맞다.

### 3-3. 설치와 업데이트를 감당해야 한다

지금은 서버 하나만 재시작하면 끝이었다. 앞으로는 PC마다 exe를 깔고, 고칠 때마다
배포해야 한다. **코드가 아니라 운영 부담이고, 계속 따라다닌다.**

**결정: 자동 업데이트를 1차 범위에 넣지 않는다.** 에이전트가 기동할 때 서버에 자기
버전을 알리고, 서버가 최소 요구 버전보다 낮으면 **작업을 주지 않고 화면에
"에이전트를 업데이트하세요"를 띄운다.** 실제 갱신은 사람이 새 exe를 받아 덮는다.
사용자가 소수인 동안은 이걸로 충분하고, 자동 업데이트는 그 자체로 별도 설계가 필요하다.

### 3-4. LLM 비용 상한은 여전히 전체 공유다

`COST_MAX_DAILY_USD_TOTAL`은 서버에 남는다. 원고 생성이 병렬로 돌면 상한에 더 빨리
닿는다. **이건 그대로 두는 게 맞다** — 상한의 목적이 전체 지출 통제이기 때문이다.
필요하면 나중에 사용자별 상한을 조정한다(이번 범위 아님).

## 4. 이미지는 문제가 아니다 — 확인함

설계 초기에 "이미지 전달이 가장 어렵다"고 판단했으나 **틀렸다.**

`api_origin`(= `http://localhost:{PORT}`)을 쓰는 곳은 `naver/editor.py:77`의
`article_html()` 하나인데, **이 함수를 부르는 곳이 테스트뿐이다.**

```
$ grep -rn "article_html(" --include=*.py | grep -v "def article_html"
apps/api/tests/test_naver_publisher.py:124, 137, 144
```

실제 자동 발행은 이미지 바이트를 그대로 들고 다닌다:

```
원고의 data URL
   ↓ naver/plan.py:331    image_bytes = _decode_data_image(src)
image_bytes (원시 바이트)
   ↓ naver/plan.py:617    NaverImageAnchor(image_bytes=...)
발행 계획
   ↓ naver/editor.py:556  _os_clipboard_image(anchor.image_bytes)
OS 클립보드 → 앵커 위치에 Ctrl+V
```

스레드도 마찬가지로 이미지를 로컬 파일로 써서 파일 업로드한다
(`threads_browser.py`의 `IMAGE_UPLOAD_*`, `cleanup_stale_thread_image_dirs`).

**둘 다 바이트만 있으면 되고 URL이 필요 없다.** 에이전트가 바이트를 손에 넣기만 하면
발행 코드는 그대로 돈다.

**결정: 작업 페이로드에 이미지를 싣지 않고, 에이전트가 따로 받아간다.**
`GET /agent/jobs/{jobId}/images/{index}`. 사진 3장이면 수 MB이고 base64는 33% 더
크다 — 큐 응답에 실으면 재시도할 때마다 다시 내려온다. 하나씩 받으면 실패한 것만
다시 받고, 큰 페이로드를 메모리에 안 올린다.

**참고:** `GET /posts/{postId}/images/{index}`(`routes.py:691`)는 그대로 둔다. 그쪽은
웹 프런트의 **복사 발행**이 쓰고(`apps/web/src/utils.ts:744`), 10분 만료 HMAC 서명으로
인증한다. 에이전트용은 기기 토큰(Bearer)을 쓰므로 라우트를 따로 둔다 — 두 인증 방식을
한 라우트에 섞지 않는다.

**낡은 문서 주의:** `docs/서버-설치-절차.md:156-157`이 "`.env`의 `PORT`가 어긋나면
네이버 발행 이미지 주소가 틀어진다"고 경고하는데, **지금 코드에는 해당하지 않는다.**
이미지 삽입이 URL 방식에서 클립보드 바이트 방식으로 바뀐 뒤 문서가 안 따라온 것이다.
이 ADR을 구현할 때 함께 고친다.

## 5. 어느 기기가 어느 작업을 받는가

### 5-1. 계정과 기기는 다른 축이다

**Blog-it 계정이 무엇으로 발행할지를 정하고, 기기가 어디서 발행할지를 정한다.**

프로필 폴더는 Blog-it 사용자별로 갈린다(`naver_profile_dir(user_id)`,
`threads_profile_dir(user_id)`). 그래서 A가 B의 PC에 앉아 **A 계정으로** 로그인해
발행하면, 크롬은 B의 PC에서 뜨지만 네이버·스레드는 **A의 계정**으로 올라간다.

엉뚱한 계정으로 올라가는 것은 이미 막혀 있다. `_session_belongs_to_settings`
(`threads_browser.py:425-437`)가 살아 있는 세션이 설정에 저장된 계정 것인지 매번
확인하고, 다르면 다시 로그인시킨다. 네이버도 같은 규칙이다(`naver/login.py`).

### 5-2. 그래서 남의 PC에서는 한 번 다시 입력해야 한다

자격증명은 그 PC의 프로필 폴더에 저장되고(`credentials.py:47`,
`profile_dir/credentials.json`), **DB에는 절대 넣지 않는다** — `routes.py:283`과
`routes.py:414`에 원칙으로 박혀 있다.

지금은 크롬이 항상 서버에서 뜨니 어느 PC로 접속하든 서버 디스크의 그 폴더가 쓰였다.
에이전트로 옮기면 **B의 PC에는 A의 폴더가 없다.** 그래서 A는 로그인 버튼만 누르는 게
아니라 **아이디·비밀번호를 다시 입력해야 한다.** 그다음부터 그 PC에서는 자동이다.

**결정: 자격증명을 서버가 배달하지 않는다.** DB에 모아 두면 한 번 털릴 때 전부 나간다.
남의 PC에서 한 번 더 입력하는 불편을 택한다.

**대가:** A의 비밀번호가 B의 PC 디스크에 (암호화되어) 남는다. A가 자리를 떠도 남는다.
그래서 설정 화면에 **"이 PC에 저장하지 않고 이번만 사용"** 옵션을 함께 만든다 —
지금 코드에는 없다(`routes.py:452-455`는 저장하거나 저장된 것을 쓰거나 둘뿐이다).

### 5-3. 어느 기기로 보낼지는 사용자가 고른다

서버는 사용자가 지금 어느 PC 앞에 앉아 있는지 알 방법이 마땅치 않다. 웹 페이지가
`127.0.0.1`의 에이전트를 찔러 자동 감지하는 방법이 있으나 브라우저의 사설 네트워크
접근 제한에 걸릴 수 있고 복잡하다.

**결정: 발행할 기기를 사용자가 목록에서 고른다.** 기본값은 마지막에 쓴 기기다.

```
발행할 PC:  [ 사무실-데스크톱 ▾ ]
            ● 사무실-데스크톱   네이버 ✓ 스레드 ✓
            ● 회의실-PC        네이버 ✗           ← 고르면 로그인 창이 뜬다
            ○ 집-노트북        (꺼짐)
```

- **수동 발행**: 고른 기기로 간다. 세션이 없으면 그 PC에서 로그인 창이 뜬다.
- **예약 발행**: 예약을 걸 때 기기를 정해 둔다. "앉아 있는 PC"라는 개념이 없기 때문이다.
  그 PC가 꺼져 있으면 3-1의 유예 정책이 적용된다.

에이전트는 heartbeat에 자기 능력을 보고한다:

```json
{ "sessions": { "naver": true, "threads": false } }
```

세션이 없는 기기도 **고를 수 있다**(로그인하면 되므로). 다만 화면에서 회색으로 표시해
"여기서는 한 번 로그인해야 한다"를 알린다. 꺼진 기기는 고를 수 없다.

어느 기기가 처리했는지는 발행 기록에 남겨 화면에 보여준다.

## 6. 단계적 전환 — 기존 경로를 지우지 않는다

**결정: `PUBLISH_MODE` 환경변수로 가른다.**

| 값 | 동작 |
|---|---|
| `server` (기본) | 지금 그대로. 서버에서 크롬을 띄운다 |
| `agent` | 에이전트 큐로 넘긴다 |

`server`가 기본인 이유: 이 ADR을 구현하는 도중에도 운영이 멈추면 안 된다. 에이전트가
검증될 때까지 기존 경로가 살아 있어야 하고, 문제가 생기면 값 하나로 되돌릴 수 있어야
한다.

**전환의 핵심 이음매:** `AgentPublisher`가 기존 `BlogPublisher` 프로토콜
(`posting/publisher.py:44`, `async def publish(job: PublishJob) -> PublishResult`)을
그대로 구현한다. 그러면 `DefaultPostingWorker`에 주입만 하면 되고 **호출부를 한 줄도
안 고친다.** 수동 발행(`blog_task/service.py:507`)도, 예약 발행(`scheduled_posting`)도
자기가 무엇과 이야기하는지 몰라도 된다.

| D4 | 예약 발행은 창을 앞으로 올리지 않는다. 인증이 필요할 때만 올린다 | 예약 시각의 방해를 줄인다 |
| D5 | 이미지는 별도 엔드포인트로 받아간다 | 페이로드 비대·재시도 낭비를 피한다 |
| D6 | 발행 기기는 사용자가 목록에서 고른다. 예약은 걸 때 기기를 정한다 | 서버는 사용자가 어느 PC 앞에 있는지 모른다 (5-3) |

| D6b | "이 PC에 저장하지 않고 이번만 사용" 옵션을 만든다 | 빌린 PC에 비밀번호를 남기지 않을 길이 필요하다 |

| D8 | 자동 업데이트는 범위 밖. 최소 버전 게이트만 둔다 | 별도 설계가 필요한 주제다 |
| D9 | `AgentPublisher`가 `BlogPublisher` 프로토콜을 구현한다 | 호출부를 안 고친다 |

## 8. 아직 정하지 않은 것

- **여러 사용자가 같은 네이버·스레드 계정을 쓰는 경우.** 두 PC에서 같은 계정으로
  동시에 로그인하면 플랫폼 쪽 이상 감지가 걸릴 수 있다. **에이전트로도 못 막는다.**
  운영 규칙으로 다뤄야 한다.
- **에이전트 로그를 서버로 모을지.** 지금은 서버 콘솔 한 곳에서 다 봤다. 흩어지면
  디버깅이 어려워진다. 1차 범위에서는 에이전트 로컬 파일에만 남기고, 필요해지면
  결과 보고에 실어 올린다.
- **에이전트가 원고 생성까지 할지.** 하지 않는다 — API 키가 배포되면 안 된다(3-4 참고).
  다만 사용자가 "내 PC에서 다 돌리고 싶다"고 하면 그때 다시 본다.
