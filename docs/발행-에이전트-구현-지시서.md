## 0. 시작 전에

### 0-1. 반드시 지키는 것

`CLAUDE.md`의 규칙이 이 문서보다 우선한다. 특히:

- **작업을 시작하면 TodoWrite로 목록을 먼저 만든다.** 단계마다 갱신한다.
- **기존 구조를 보존하고 최소한으로 바꾼다.** 요청받지 않은 리팩터링을 넣지 않는다.
- **한국어로 쓴다.** 주석·독스트링·로그·에러 메시지·테스트 이름·커밋 메시지 전부.
- **단계를 끝낼 때마다 `변경내역/YYYY-MM-DD-변경내역.md`에 기록하고 커밋한다.**
  하지 않은 것과 확인하지 못한 것도 적는다.
- **푸시는 명시적으로 요청받았을 때만 한다.**

### 0-2. 검증 명령

각 단계 끝에서 돌린다.

```bash
cd apps/api && python -m pytest        # 백엔드
cd apps/web && npm test -- --run       # 프런트엔드
cd apps/web && npm run build           # tsc -b && vite build
```

**사전에 존재하는 실패 14건이 있다** — Windows 임시폴더 권한 문제(`PermissionError:
[WinError 5] ... pytest-of-winzrnd`)로 `test_naver_publisher.py`·`test_publisher.py`·
`test_trend_sources.py`에서 난다. 내 변경 탓이 아니므로 쫓지 않는다.
**그 외의 실패는 반드시 원인을 찾는다.**

### 0-3. Mongo 검증기 함정

저장 모델에 **필드를 더하는 것**은 검증기가 `additionalProperties: true`라 그냥 통과한다.
**필드를 지우거나 새 컬렉션을 만들 때는** `apps/api/scripts/init_mongo.py`를 함께 고치고
다시 실행해야 한다. 안 하면 저장이 거부된다.

```bash
cd apps/api && python scripts/init_mongo.py
```

### 0-4. 단계는 순서대로, 각각 독립 커밋

1~8단계는 앞 단계에 의존한다. **건너뛰지 않는다.** 각 단계가 끝나면 테스트가 통과하고
운영이 깨지지 않는 상태여야 한다 — `PUBLISH_MODE=server`(기본)인 한 4단계까지는 실제
동작이 하나도 안 바뀐다.

## 3. 1단계 — `PUBLISH_MODE` 스위치

**목표:** 아무 동작도 바뀌지 않는 상태에서 갈림길만 만든다.

### 할 일

1. `apps/api/app/config.py`에 추가:

```python
def publish_mode() -> str:
    """발행을 어디서 하는가. `server`(기본) 또는 `agent`.

    `agent`로 두면 발행 작업이 사용자 PC의 에이전트 큐로 넘어간다
    (docs/발행-에이전트-설계.md). 검증이 끝날 때까지 기본은 `server`다 —
    값 하나로 되돌릴 수 있어야 운영을 멈추지 않고 옮길 수 있다.
    """
    value = (os.environ.get("PUBLISH_MODE") or "server").strip().lower()
    return value if value in {"server", "agent"} else "server"
```

2. `.env.example`에 주석과 함께 `PUBLISH_MODE=server` 추가.
3. `README.md`의 환경변수 표에 한 줄 추가.

### 테스트

`apps/api/tests/test_config.py`(없으면 신설)에:
- 값이 없으면 `server`
- `agent`면 `agent`
- 알 수 없는 값(`AGENT!`, 빈 문자열)이면 `server`로 떨어진다

### 하지 말 것

- 이 단계에서 `publish_mode()`를 **아무도 부르지 않는다.** 3단계에서 연결한다.

## 4. 2단계 — 기기 등록과 인증

**목표:** 사용자가 자기 PC를 계정에 묶고, 에이전트가 토큰으로 서버를 부를 수 있게.

### 4-1. Mongo 컬렉션 `agent_devices`

`apps/api/scripts/init_mongo.py`의 `COLLECTIONS`에 추가한다. 기존 항목
(`scheduled_jobs`, `brand_profiles`)의 모양을 그대로 따른다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `deviceId` | string | UUID |
| `userId` | string | 소유자 |
| `name` | string | 사람이 알아볼 이름 (예: `사무실-데스크톱`) |
| `tokenHash` | string | 기기 토큰의 SHA-256. **토큰 원문은 저장하지 않는다** |
| `agentVersion` | string | 에이전트가 보고한 버전 |
| `sessions` | object | `{ "naver": bool, "threads": bool }` |
| `lastSeenAt` | date | 마지막 heartbeat |
| `createdAt` | date | |
| `revokedAt` | date \| null | 해지되면 값이 찬다 |

인덱스:
- `deviceId` unique
- `(userId, lastSeenAt)` — 화면 목록용
- `tokenHash` unique — 인증 조회

**required:** `deviceId userId name tokenHash createdAt`

### 4-2. 페어링 코드

메모리에만 둔다. **Mongo에 넣지 않는다** — 수명이 5분이고, 서버가 재시작되면
사용자가 다시 발급하면 그만이다.

```python
# modules/agent/service.py
PAIRING_CODE_TTL_SECONDS = 300
PAIRING_CODE_LENGTH = 6          # 숫자 6자리. 사람이 옮겨 적는다
```

- 발급: 사용자당 **하나만** 유효하다. 다시 요청하면 이전 것을 버린다.
- 소진: 한 번 쓰면 즉시 무효.
- 실패: 코드가 틀리면 `error_response(400, "PAIRING_CODE_INVALID", ...)`.
  **몇 번 틀렸는지 세어 5회 초과면 그 코드를 버린다** — 6자리는 무차별 대입이 쉽다.

### 4-3. 기기 토큰

- 발급: `secrets.token_urlsafe(32)`
- 저장: 서버에는 `hashlib.sha256(token).hexdigest()`만. 원문은 발급 응답에 한 번만.
- 검증: `Authorization: Bearer <token>` → 해시로 조회 → `revokedAt`이 없고 유효하면 통과
- **사용자 로그인 토큰(`modules/auth/token.py`)과 섞지 않는다.** 별도 함수로 검증한다.

```python
# http/routes.py
async def _authenticate_device(request: Request) -> AgentDevice:
    """에이전트 전용 인증. 사람 로그인 토큰은 여기서 통하지 않는다."""
```

## 5. 3단계 — 작업 큐

**목표:** 서버가 발행 작업을 쌓고, 에이전트가 하나씩 집어 결과를 돌려준다.

### 5-1. Mongo 컬렉션 `agent_jobs`

| 필드 | 타입 | 설명 |
|---|---|---|
| `agentJobId` | string | UUID |
| `userId` | string | |
| `postId` | string | `BlogTask`의 id |
| `channel` | string | `NAVER` \| `THREADS` |
| `method` | string | `DRAFT` \| `AUTO` |
| `origin` | string | `MANUAL` \| `SCHEDULED` — 창을 앞으로 올릴지 정한다 (설계 D4) |
| `targetDeviceId` | string | **이 작업을 처리할 기기.** 사용자가 발행 화면에서 고른다 (설계 D6) |
| `payload` | object | `threadsTexts`, `threadsTopic` 등. **이미지는 안 넣는다** |
| `status` | string | 아래 상태 머신 |
| `deviceId` | string \| null | 실제로 집어간 기기 (`targetDeviceId`와 같아야 정상) |
| `attempts` | int | 집힌 횟수 |
| `claimedAt` | date \| null | |
| `heartbeatAt` | date \| null | 실행 중 갱신 |
| `result` | object \| null | `{ result, postUrl, errorMessage }` |
| `notBefore` | date \| null | 이 시각 전에는 집히지 않는다 (예약) |
| `expiresAt` | date \| null | 유예 마감 (설계 D3) |
| `createdAt` / `updatedAt` | date | |

인덱스:
- `agentJobId` unique
- `(targetDeviceId, status, notBefore)` — claim 조회
- `(status, heartbeatAt)` — 유령 작업 회수

**required:** `agentJobId userId postId channel method origin targetDeviceId status createdAt`

### 5-2. 상태 머신

```
QUEUED ──claim──> CLAIMED ──(작업 시작)──> RUNNING ──> SUCCEEDED
   │                  │                       │    └──> FAILED
   │                  │                       │    └──> NEEDS_HUMAN
   │                  └──(heartbeat 끊김)──────┘         │
   │                          ↓                          │
   └──────────────────── QUEUED (attempts += 1) ─────────┘
   │
   └──(expiresAt 초과)──> EXPIRED
```

- **heartbeat가 90초 끊기면 `QUEUED`로 되돌린다.** 에이전트가 죽거나 PC가 꺼진 경우다.
- `attempts >= 3`이면 되돌리지 않고 `NEEDS_HUMAN`으로 넘긴다. 무한 재시도를 막는다.
- `EXPIRED`는 예약 유예(기본 2시간)를 넘긴 것이다. 예약 작업 상태도 `NEEDS_HUMAN`이 된다.

### 5-3. 라우트

| 메서드 | 경로 | 인증 | 설명 |
|---|---|---|---|
| POST | `/agent/heartbeat` | 기기 | 살아 있음 + 세션 능력 보고 |
| POST | `/agent/jobs/claim` | 기기 | 작업 하나 집기 (없으면 204) |
| GET | `/agent/jobs/{id}/images/{index}` | 기기 | 이미지 바이트 |
| POST | `/agent/jobs/{id}/heartbeat` | 기기 | 실행 중 갱신 |
| POST | `/agent/jobs/{id}/result` | 기기 | 결과 보고 |

```jsonc
// POST /agent/heartbeat
//   { "sessions": { "naver": true, "threads": false }, "agentVersion": "0.1.0" }
//   →  200
{ "ok": true, "minAgentVersion": "0.1.0" }   // 낮으면 에이전트가 스스로 멈춘다

// POST /agent/jobs/claim   →  200 (일감 있음)
{
  "agentJobId": "…",
  "postId": "…",
  "channel": "NAVER",
  "method": "AUTO",
  "origin": "SCHEDULED",
  "title": "…",
  "htmlContent": "…",
  "hashtags": ["…"],
  "imageCount": 3,
  "threadsTexts": null,
  "threadsTopic": null
}
//   →  204 (일감 없음)
```

**claim은 원자적이어야 한다.** Mongo의 `find_one_and_update`로
`status: QUEUED` → `CLAIMED`를 한 번에 바꾼다. 재시도로 같은 작업이 두 번 집히는
것을 막는다.

**claim 필터는 기기 지정이다** (설계 D6): `targetDeviceId == 이 기기`인 작업만 준다.
사용자가 발행 화면에서 기기를 골랐으므로 서버가 능력을 보고 고르지 않는다.
`sessions` 보고는 **화면 표시용**이다 — 세션 없는 기기는 회색으로 그려 "여기서는
한 번 로그인해야 한다"를 알린다. 세션이 없어도 사용자가 고르면 작업은 간다
(그 PC에서 로그인 창이 뜬다).

### 5-4. 이미지 라우트

`GET /agent/jobs/{id}/images/{index}` — 기기 토큰(Bearer)으로 인증하고,
그 기기가 **그 작업을 집은 기기인지** 확인한 뒤 바이트를 돌려준다.

기존 `GET /posts/{postId}/images/{index}`(`routes.py:691`)는 **건드리지 않는다.**
그쪽은 HMAC 서명으로 인증하고 웹 프런트의 복사 발행이 쓴다. 두 인증 방식을 한
라우트에 섞지 않는다.

바이트를 꺼내는 부분은 그 라우트의 구현을 그대로 참고한다
(`task.final_post.images[index]`의 data URL을 디코드).

### 테스트 (`apps/api/tests/test_agent_queue.py` 신설)

- 같은 작업을 두 번 claim하면 두 번째는 빈손이다 (원자성)
- `notBefore`가 미래인 작업은 안 집힌다
- `targetDeviceId`가 다른 기기는 그 작업을 못 집는다
- heartbeat가 90초 끊기면 `QUEUED`로 돌아가고 `attempts`가 는다
- `attempts >= 3`이면 `NEEDS_HUMAN`이 된다
- `expiresAt`을 넘기면 `EXPIRED`가 된다
- 다른 기기가 남의 작업에 결과를 보고하면 거부된다
- 다른 기기가 남의 작업 이미지를 받으려 하면 404

## 6. 4단계 — `AgentPublisher`

**목표:** 기존 호출부를 한 줄도 안 고치고 발행을 큐로 넘긴다.

### 할 일

`apps/api/app/posting/agent_publisher.py` 신설.

```python
class AgentPublisher:
    """발행을 사용자 PC의 에이전트에 넘긴다.

    ``BlogPublisher`` 프로토콜(publisher.py:44)을 그대로 구현하므로 부르는 쪽은
    자기가 무엇과 이야기하는지 몰라도 된다 — 수동 발행도 예약 발행도 안 고친다.
    """

    async def publish(self, job: PublishJob) -> PublishResult:
        # 1) job.target_device_id의 기기가 온라인인가?
        #    아니면 **기다리지 않고** 바로 NEEDS_HUMAN을 돌려준다.
        #    (PC가 꺼져 있는데 15분씩 붙잡고 있으면 화면이 멎는다)
        # 2) agent_jobs에 QUEUED로 넣는다 (targetDeviceId 포함)
        # 3) 결과가 올 때까지 기다린다 (AGENT_RESULT_TIMEOUT_SECONDS)
        # 4) 시간을 넘기면 NEEDS_HUMAN
```

**`PublishJob`에 필드 하나를 더한다** (`posting/publisher.py:21`):

```python
# 발행을 처리할 기기. 사용자가 발행 화면에서 고른다(설계 D6).
# 서버 발행(PUBLISH_MODE=server)에서는 쓰이지 않으므로 기본 None —
# 옛 호출·저장된 옛 작업이 그대로 돌아야 한다.
target_device_id: str | None = None
```

값은 발행 요청 본문에서 온다: `POST /posts/{id}/publish`의 body에 `deviceId`를
추가하고 `_validate_publish_request`에서 읽는다. **없으면 그 사용자의 기기가 하나뿐일
때 그것으로, 여럿이면 `error_response(400, "DEVICE_REQUIRED", ...)`** — 조용히
아무 기기나 고르지 않는다.

```python
AGENT_RESULT_TIMEOUT_SECONDS = 900   # 15분. 네이버 발행 실측(수 분)의 3배 남짓
```

기다리는 방법은 **폴링**으로 한다(0.5초 간격). asyncio 이벤트로 깨우는 방식은
서버가 여러 대로 늘면 안 통한다 — 지금은 한 대지만 폴링이 그때도 그대로 돈다.

### 주입

```python
# apps/api/app/services.py:147 부근
posting_worker=DefaultPostingWorker(
    auto_publisher=AgentPublisher() if publish_mode() == "agent" else None,
    threads_publisher=AgentPublisher() if publish_mode() == "agent" else None,
),
```

`None`이면 `DefaultPostingWorker`가 기존 기본값을 쓴다(`publisher.py:148-150`).
**`copy_publisher`는 건드리지 않는다** — 복사 발행은 클립보드가 목적지라 브라우저를
안 쓴다.

### 테스트 (`apps/api/tests/test_agent_publisher.py` 신설)

- 온라인 기기가 없으면 즉시 `NEEDS_HUMAN`이고 큐에 넣지 않는다
- 큐에 넣고 결과가 오면 그대로 `PublishResult`로 돌려준다
- 타임아웃이면 `NEEDS_HUMAN`이고 메시지에 이유가 있다
- `PUBLISH_MODE=server`면 `AgentPublisher`가 아예 조립되지 않는다 (기존 동작 회귀 테스트)

### 하지 말 것

- `blog_task/service.py`의 `publish_blog_task`를 고치지 않는다.
- `scheduled_posting/worker.py`를 이 단계에서 고치지 않는다. 6단계에서 한다.

## 7. 5단계 — 에이전트 골격

**목표:** 서버에 붙어 heartbeat를 보내고 작업을 집어오는 프로그램. 아직 발행은 안 한다.

### 구조

```
apps/agent/blogit_agent/
  main.py       폴링 루프. Ctrl+C로 깨끗이 종료
  config.py     서버 주소·기기 토큰을 %LOCALAPPDATA%\Blog-it\agent.json에 저장
  client.py     httpx로 서버 호출. 재시도·백오프
  session.py    프로필 폴더를 보고 naver/threads 세션 보유 판정
  tray.py       pystray 트레이 아이콘. 상태 표시·알림·종료
  runner.py     (6단계에서 채운다)
```

### 폴링 루프

```
30초마다  POST /agent/heartbeat
 5초마다  POST /agent/jobs/claim
          → 204면 아무것도 안 한다
          → 200이면 runner에 넘기고, 끝날 때까지 claim을 멈춘다  ← 이것이 단일 큐다
```

**한 번에 하나만 처리한다.** 이 한 줄이 클립보드 충돌과 프로필 잠금을 막는 전부다
(설계 1-1, 1-4). 병렬로 돌리고 싶은 유혹이 생기면 설계 문서를 다시 읽는다.

### 세션 보유 판정 (`session.py`)

서버 코드의 판정을 그대로 옮긴다:
- 네이버: `posting/naver`의 세션 쿠키 확인 로직
- 스레드: `threads_browser.has_threads_session(profile_dir)`

프로필 경로도 서버와 같은 규칙을 쓴다 — `threads_profile_dir(user_id)`
(`threads_browser.py:179-189`)가 `user_id`를 sha256으로 잘라 폴더를 만든다.
**에이전트는 자기 사용자 하나만 쓰므로 그 사용자의 폴더 하나만 본다.**

### 설정 파일

```jsonc
// %LOCALAPPDATA%\Blog-it\agent.json
{
  "serverUrl": "http://192.168.0.10:8888",
  "deviceId": "…",
  "token": "…"
}
```

**파일 권한을 소유자 전용으로 만든다.** `modules/auth/token.py`의 `.auth-secret`
생성 코드(`os.open`에 권한 플래그)를 참고한다.

### 첫 실행 (페어링)

토큰이 없으면 콘솔로 물어본다:

```
서버 주소를 입력하세요: http://192.168.0.10:8888
Blog-it 화면에서 발급한 6자리 코드: 482913
이 PC의 이름: 사무실-데스크톱
→ 등록되었습니다. 트레이에서 상태를 볼 수 있습니다.
```

### 테스트

에이전트는 pytest 대상에 넣지 않는다(별도 앱이고 CI가 없다). 대신 **`--selftest`
플래그**를 만든다 — 서버에 붙어 heartbeat 한 번을 보내고 결과를 출력하고 끝난다.
설치 후 확인용이다.

## 8. 6단계 — 발행 코드 이식

**목표:** 에이전트가 실제로 크롬을 띄워 발행한다.

### 옮기는 것

`apps/api/app/posting/` 아래에서 **브라우저를 만지는 부분만** 에이전트로 복사한다:

```
naver/browser.py  naver/login.py  naver/editor.py  naver/plan.py
naver/clipboard.py  naver/constants.py
threads_browser.py  threads_split.py
credentials.py  credential_crypto.py
```

**서버에서 지우지 않는다.** `PUBLISH_MODE=server`가 살아 있어야 하기 때문이다(설계 D7).

> **중복이 생긴다. 의도한 것이다.** 지금 단계에서 공용 패키지로 뽑으면 서버와
> 에이전트가 동시에 흔들려 무엇이 깨졌는지 알 수 없게 된다. 에이전트가 검증되고
> `PUBLISH_MODE=server` 경로를 지우기로 결정한 뒤에 정리한다.

### `runner.py`가 하는 일

```
1. claim 응답에서 원고를 받는다
2. imageCount만큼 GET /agent/jobs/{id}/images/{n} 로 바이트를 받는다
3. FinalPost와 PublishJob을 서버와 같은 모양으로 조립한다
4. origin == "SCHEDULED"면 bring_to_front를 끈다            ← 설계 D4
   origin == "MANUAL"이면 지금처럼 앞으로 올린다
5. 기존 발행 코드를 부른다
6. 30초마다 POST /agent/jobs/{id}/heartbeat
7. 끝나면 POST /agent/jobs/{id}/result
```

### 자격증명은 이 PC 것만 쓴다 (설계 D6a)

**서버는 네이버·스레드 아이디·비밀번호를 보내지 않는다.** 에이전트는 자기 PC의
프로필 폴더(`credentials.json`)만 읽는다 — 서버 코드의 `load_credentials`를 그대로
가져가면 된다.

세션도 저장된 자격증명도 없으면 크롬에 **로그인 창을 띄우고 사람을 기다린다**(수동
발행일 때). 사용자가 로그인하면 그 PC에 세션이 남아 다음부터 자동이다. **예약 발행일
때는 기다리지 않고** `NEEDS_HUMAN`으로 보고한다 — 아무도 없는 PC에서 로그인 창을
띄워 봐야 타임아웃만 태운다.

**"이 PC에 저장하지 않고 이번만 사용" (설계 D6b):** 로그인 창에서 사용자가 입력한
자격증명을 `credentials.json`에 **쓰지 않는 길**을 둔다. 세션 쿠키는 남는다(그건
크롬 프로필의 일이다). 비밀번호 파일만 안 만든다.

### `bring_to_front` 제어

`naver/browser.py:468`이 지금은 `if not headless:`로만 판단한다. 에이전트 쪽 복사본에
플래그를 하나 더 받게 한다:

```python
if not headless and bring_forward:
    bring_to_front(driver)
```

2단계 인증·캡차를 만나면 **그때는 무조건 앞으로 올리고 트레이 알림을 띄운다.**
사람이 필요한 순간이라 방해하는 것이 맞다.

### 이미지 임시 파일

스레드 발행은 이미지를 파일로 쓴다. 서버의 `cleanup_stale_thread_image_dirs`와
`THREAD_IMAGE_STALE_SECONDS`(24시간)를 그대로 가져간다. **에이전트 종료 시에도
한 번 정리한다** — 사용자 PC에 쓰레기를 쌓지 않는다.

### 검증 (사람이 직접)

자동 테스트로 덮을 수 없다. 다음을 **실제로 해 보고 결과를 변경내역에 적는다:**

1. 네이버 수동 발행 1건 — 본문·이미지·해시태그가 다 들어갔는가
2. 스레드 수동 발행 1건 — 연속 스레드와 이미지가 순서대로 올라갔는가
3. 예약 발행 1건 — 창이 앞으로 안 튀어나오는가
4. 예약 발행 중 2단계 인증 — 창이 앞으로 오고 알림이 뜨는가
5. **PC 두 대에서 동시에 발행** — 본문이 섞이지 않는가 ← 이 설계의 존재 이유

## 9. 7단계 — 오프라인 유예 정책

**목표:** PC가 꺼져 있어도 완성된 원고를 버리지 않는다 (설계 D3).

### 할 일

1. 상수:

```python
# modules/agent/service.py
AGENT_GRACE_PERIOD_SECONDS = 2 * 60 * 60   # 2시간
```

환경변수 `AGENT_GRACE_PERIOD_HOURS`로 덮을 수 있게 한다.

2. 예약 작업이 `READY_TO_PUBLISH`가 되고 발행 시각이 오면, `agent_jobs`에
   `notBefore = publish_at`, `expiresAt = publish_at + 유예`,
   `targetDeviceId = 예약에 지정된 기기`로 넣는다.

   **`ScheduledJob` 모델에 `deviceId` 필드를 더한다** — 예약을 걸 때 고른 기기다
   (설계 5-3). 옛 작업 문서에는 없으므로 **기본 None**, None이면 그 사용자의 기기가
   하나뿐일 때 그것을 쓰고 여럿이면 `NEEDS_HUMAN`으로 넘긴다(조용히 아무 기기나
   고르지 않는다). 모델의 다른 필드들이 같은 방식으로 기본값을 두고 있다
   (`models.py:198-215`의 `series_id`·`subject_category` 참고).

3. 유예 안에 에이전트가 붙으면 **그 즉시** 집어간다(5초 폴링이라 실질 즉시).

4. 유예를 넘기면 `agent_jobs.status = EXPIRED`, 예약 작업은 `NEEDS_HUMAN`.
   `ScheduledLogEntry`에 사용자가 읽을 한 줄을 남긴다:

   > 예약 시각에 발행 PC가 꺼져 있어 2시간을 기다렸습니다. PC를 켜고 다시 발행해 주세요.

   **비밀번호·토큰·셀레니움 스택을 여기 담지 않는다**(`models.py:166-171`).

5. `scheduled_posting/worker.py`의 `_publishing` 단일 슬롯은 **`PUBLISH_MODE=agent`일 때
   의미가 없어진다** — 직렬화는 에이전트가 한다. 그래도 **지우지 않는다.**
   `server` 모드에서 여전히 필요하다.

### 테스트 (`test_agent_queue.py`에 추가)

- 예약 시각 전에는 안 집힌다
- 예약 시각 후 에이전트가 붙으면 집힌다
- 유예를 넘기면 `EXPIRED`가 되고 예약 작업이 `NEEDS_HUMAN`이 된다
- 유예 안에 붙으면 늦어도 발행된다
- `NEEDS_HUMAN` 로그에 민감정보가 없다

## 10. 8단계 — 화면

**목표:** 사용자가 기기를 등록하고 상태를 본다.

### 설정 화면에 "발행 PC" 섹션

```
발행 PC
─────────────────────────────────────
● 사무실-데스크톱      네이버 ✓  스레드 ✓   방금 전
○ 집-노트북           네이버 ✓  스레드 ✗   3일 전     [해지]

[새 PC 연결하기]  → 6자리 코드와 안내를 보여준다
```

- `online`이면 채운 원, 아니면 빈 원
- 세션이 없는 채널은 회색으로 — "이 PC에서 발행하면 한 번 로그인해야 합니다"를 알린다

### 발행 화면에 기기 선택 (설계 D6)

수동 발행 버튼 옆에 기기 선택을 둔다:

```
발행할 PC:  [ 사무실-데스크톱 ▾ ]     ← 기본값: 마지막에 발행에 쓴 기기
```

- 선택값이 `POST /posts/{id}/publish`의 `deviceId`로 간다
- 꺼진 기기는 고를 수 없다(목록에 흐리게 표시)
- 기기가 하나뿐이면 선택 UI를 숨기고 그것을 쓴다
- **온라인 기기가 하나도 없으면 발행 버튼을 막고 경고를 띄운다:**
  > 발행할 PC가 연결되어 있지 않습니다. 에이전트를 켜 주세요.

**예약 화면에도 같은 선택을 둔다.** 예약을 걸 때 기기를 정해 두는 것이다 —
발행 시각에 "앉아 있는 PC"라는 개념이 없기 때문이다(설계 5-3).

### 발행 결과에 기기 이름

발행 기록(`postingLogs`)에 어느 기기가 처리했는지 보여준다. 기기가 여럿일 때
"왜 저 PC에서 떴지"를 설명해 준다.

### 기존 기능 보존 확인

- `PUBLISH_MODE=server`에서 화면이 예전 그대로 동작하는가 — **기기 선택 UI가
  숨겨지는가** (서버 모드에서는 의미가 없다)
- 기기가 하나도 없는 계정에서 화면이 깨지지 않는가
- 옛 `postingLogs`(기기 정보 없음)가 그대로 읽히는가 ← **기본값을 준다**
- 옛 예약 작업(기기 지정 없음)이 그대로 읽히는가 ← **기본값을 준다**

## 11. 9단계 — 마무리

1. **`docs/서버-설치-절차.md:156-157`의 낡은 경고를 고친다.**
   `.env`의 `PORT`가 네이버 발행 이미지 주소를 정한다는 설명은 지금 코드에 해당하지
   않는다. 이미지는 클립보드 바이트로 다닌다(설계 4절). `PORT`는 리슨 포트만 정한다.

2. **`README.md`에 에이전트 설치 절차를 추가한다.**
   `apps/agent/README.md`에는 상세를, README에는 링크와 요약만.

3. **`article_html()`이 죽은 코드인지 판단한다.**
   `posting/__init__.py:30`에서 export되지만 테스트만 부른다. 지우려면 별도 작업으로
   올린다 — **이 지시서의 범위가 아니다.**

4. **`PUBLISH_MODE=agent`를 기본으로 바꿀지 결정한다.** 위 6단계의 사람 검증 5개가
   모두 통과하고 2주 이상 운영이 안정된 뒤에만 한다.

## 13. 완료 판정

아래가 전부 참이면 끝난 것이다.

- [ ] `PUBLISH_MODE=server`에서 지금과 **똑같이** 동작한다 (회귀 없음)
- [ ] `PUBLISH_MODE=agent`에서 수동 발행이 사용자 PC 크롬에서 뜬다
- [ ] 예약 발행이 사용자 PC 크롬에서 뜨고, 창이 앞으로 튀어나오지 않는다
- [ ] **PC 두 대에서 동시에 발행해도 본문이 섞이지 않는다**
- [ ] PC가 꺼져 있으면 유예 동안 기다렸다가, 켜면 발행된다
- [ ] 유예를 넘기면 `NEEDS_HUMAN`이 되고 사용자가 읽을 안내가 남는다
- [ ] 작업은 지정된 기기(`targetDeviceId`)만 집는다
- [ ] A가 B의 PC에서 A 계정으로 발행하면 그 PC에서 창이 뜨되, 네이버·스레드는 A의 계정으로 올라간다
- [ ] "이 PC에 저장하지 않고 이번만 사용"으로 로그인하면 `credentials.json`이 안 생긴다
- [ ] `python -m pytest`가 **사전 실패 14건 외에** 통과한다
- [ ] `npm test -- --run`과 `npm run build`가 통과한다
- [ ] 단계마다 `변경내역/`에 기록이 남았다 — **하지 않은 것과 확인 못 한 것 포함**
