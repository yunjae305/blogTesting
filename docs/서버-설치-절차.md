# Windows Server 설치 절차

회사 Windows Server에 Blog-it을 올리는 순서다. **기존 서버 설정을 건드리지 않고**, 백엔드
하나를 `127.0.0.1:8001`에 띄운 뒤 마지막에 Nginx를 붙인다.

보안 이관(암호화 키, 네이버·Threads 자격증명, ACL)은
[Windows Server 보안 배포](Windows-Server-보안-배포.md)에 따로 있다. 이 문서는 "일단 뜨게
하는" 절차다.

---

## 운영 구조

```text
회사 고정 IP:8888
      ↓
Nginx :8888                    ← 기존 것. location / 하나만 추가한다
      ↓
127.0.0.1:8001
      ↓
FastAPI  (프로세스 하나)
 ├─ API
 ├─ apps/web/dist 화면
 ├─ 발행용 이미지 제공
 └─ Selenium → Chrome         ← GUI 세션이 필요한 부분
      ↓
MongoDB
```

**프런트엔드를 따로 띄우지 않는다.** 운영에서는 FastAPI가 API와 화면을 같은 포트에서
함께 서빙한다 — `app/main.py`가 `apps/web/dist`를 정적 파일로 마운트한다.

작업 순서로 보면 이렇다.

```text
[변경 안 함]  고정 IP · Nginx 8888 · MongoDB · 기존 서버 설정
      ↓
[추가]        Node · Python venv · Blog-it 코드 · 백엔드 127.0.0.1:8001
      ↓
[확인]        http://localhost:8001  ← 화면과 API가 모두 여기
      ↓
[마지막]      Nginx  →  127.0.0.1:8001
```

`apps/web/vite.config.ts`의 프록시는 `server.proxy`, 즉 **`npm run dev` 전용**이다.
`vite preview`에는 적용되지 않으므로 프런트를 별도 포트에 띄우면 API 요청이 어디에도
닿지 않는다. 굳이 나누려면 `preview.proxy`를 새로 만들고 CORS까지 열어야 하는데, 얻는
것이 없다.

## 0. 서버에 미리 있어야 할 것

| 항목 | 요구 | 확인 |
| --- | --- | --- |
| Node.js | 22 이상 (검증에 쓴 것은 v24.18.0) | `node --version` |
| Python | 3.11 이상 | `python --version` |
| Git | 코드를 clone 한다면 | `git --version` |
| MongoDB | 접속 가능한 인스턴스 | `mongosh --eval "db.runCommand({ping:1})"` |
| Google Chrome | 네이버·스레드 발행에 쓴다 | 설치 여부 |

Chrome은 **발행 기능을 쓸 때만** 필요하다. 글 생성까지만 쓸 거면 없어도 된다.

## 1. 코드 가져오기

```powershell
cd C:\apps                     # 원하는 위치
git clone https://github.com/g-rnd-winz/Blog-it.git
cd Blog-it
```

## 2. 프런트엔드 빌드

**저장소 루트에서 실행한다.** `apps/web`이 아니다 — 루트 `package.json`이 워크스페이스로
`apps/web`을 관리하므로, 하위 폴더에서 `npm ci`를 돌리면 의존성이 어긋난다.

```powershell
npm ci
npm run build
```

`apps/web/dist`가 생기면 성공이다. 이 폴더가 곧 화면이고, 백엔드가 이걸 서빙한다.

```powershell
Test-Path apps\web\dist\index.html    # True 여야 한다
```

## 3. Python 가상환경과 의존성

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r apps/api/requirements.txt
```

`Activate.ps1`이 실행 정책에 막히면 그 세션에서만 풀어 준다.

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

## 4. `.env` 만들기

저장소 **루트**에 둔다. 백엔드는 실행 위치와 무관하게 루트에서 `.env`를 찾는다.

```powershell
Copy-Item .env.example .env
notepad .env
```

운영에서 반드시 바꿀 값이다.

```ini
PORT=8001
APP_ENV=production
MONGODB_URI=mongodb://localhost:27017/blog_it
BLOGIT_CHROME_NO_SANDBOX=false

# 없으면 서버가 시작을 거부한다 — 아래 '이거 빼면 안 뜬다' 참고
AUTH_TOKEN_SECRET=<32바이트 이상>
EMAIL_ENC_KEY=<32바이트 base64url>
EMAIL_INDEX_KEY=<32바이트 base64url>

ANTHROPIC_API_KEY=<필수>
GOOGLE_API_KEY=<필수>
OPENAI_API_KEY=<필수>
```

### 이거 빼면 안 뜬다

`PORT`·`APP_ENV`·AI 키만 적으면 **서버가 기동 중에 멈춘다.** 실제로 재본 결과다
(2026-08-13, `APP_ENV=production` 기준).

| 빠진 값 | 어디서 멈추나 | 실제 메시지 |
| --- | --- | --- |
| `AUTH_TOKEN_SECRET` | lifespan 첫 단계 | `운영 환경에서는 AUTH_TOKEN_SECRET을 외부 secret store에서 주입해야 합니다.` |
| `EMAIL_ENC_KEY`·`EMAIL_INDEX_KEY` | Mongo 저장소 조립 | `이메일을 암호화하려면 EMAIL_ENC_KEY, EMAIL_INDEX_KEY 환경변수가 필요합니다.` |

`AUTH_TOKEN_SECRET`이 먼저 터지므로, 그것만 채우고 다시 띄우면 이번엔 이메일 키에서
멈춘다. 셋을 한 번에 채우는 편이 빠르다.

### 반대로 안 적어도 되는 것

`APP_ENV=production`이 이 둘을 알아서 처리한다 — 실측으로 확인했다.

| 값 | production일 때 | 그래서 |
| --- | --- | --- |
| `CORS_ALLOWED_ORIGINS` | 기본이 빈 목록 `[]` | 화면과 API가 같은 origin이라 적을 것이 없다 |
| `ALLOW_IN_MEMORY_STORAGE` | 기본이 `False` | Mongo가 죽으면 메모리로 숨지 않고 실패한다 |

`MONGODB_URI`도 로컬 MongoDB(27017)를 쓴다면 생략할 수 있다 — 기본값이
`mongodb://localhost:27017/blog_it`이다. 다만 명시해 두는 편이 나중에 헷갈리지 않는다.

**`PORT`는 실제 리슨 포트와 같게 적는다.** uvicorn `--port`와 `.env`의 `PORT`가
다르면 값이 서로 어긋난 채 돈다 — 어느 쪽이 진짜인지 사람이 헷갈리고, nginx의
`proxy_pass` 대상과도 안 맞게 된다.

(예전에 이 자리에 "PORT가 어긋나면 네이버 발행 이미지 주소가 틀어진다"고 적혀
있었는데, **지금 코드에는 해당하지 않는다** — 2026-08-14 확인. 자동 발행은 이미지를
URL이 아니라 클립보드 바이트로 넣는다(`posting/naver/plan.py` → `editor.py`). URL을
만들던 `article_html()`은 테스트에서만 불린다.)

**AI 키 셋은 없으면 서버가 시작을 거부한다.** 빠진 키를 한 번에 알려 준다.

키 생성:

```powershell
python -c "import base64,secrets;print(base64.urlsafe_b64encode(secrets.token_bytes(32)).decode().rstrip('='))"
```

- **DB를 새로 시작한다면** `EMAIL_ENC_KEY`·`EMAIL_INDEX_KEY`·`AUTH_TOKEN_SECRET`을 위
  명령으로 새로 만든다.
- **지금 PC의 DB를 옮겨 쓴다면** `EMAIL_INDEX_KEY`는 **현재 값 그대로** 가져와야 한다.
  바꾸면 기존 계정 로그인과 중복 검사가 전부 깨진다.

## 5. MongoDB 초기화

**이 단계를 빠뜨리기 쉽다.** 컬렉션·JSON 스키마 검증기·유니크 인덱스를 만든다. 안 하면
가입이나 저장이 거부된다.

```powershell
python apps/api/scripts/check_mongo.py    # 어디에 붙는지 먼저 확인
python apps/api/scripts/init_mongo.py
```

### 회사 MongoDB를 쓸 때

`init_mongo.py`는 **대상 DB에 실제로 쓴다.** 남의 DB에 붙어 있는 채로 돌리지 않도록
`check_mongo.py`로 접속 대상을 먼저 확인한다.

하는 일과 필요 권한이다.

| 하는 일 | 명령 | 필요 역할 |
| --- | --- | --- |
| 컬렉션 생성 | `createCollection` | `readWrite` |
| 검증기 갱신(이미 있는 컬렉션) | `collMod` | `dbAdmin` |
| 유니크 인덱스 생성 | `createIndex` | `readWrite` |

즉 대상 DB에 대해 **`readWrite` + `dbAdmin`**(또는 `dbOwner`)이 필요하다. 읽기 전용
계정으로는 이 단계에서 막힌다.

접속 문자열은 이렇게 쓴다.

```ini
MONGODB_URI=mongodb://<사용자>:<비밀번호>@<호스트>:27017/blog_it?authSource=admin
```

- **끝에 DB 이름(`/blog_it`)을 반드시 붙인다.** 없으면 드라이버가
  "No default database name defined"로 실패한다
- 비밀번호에 `@ / ? # :` 가 있으면 **URL 인코딩**한다 (`@` → `%40`)
- 인증 DB가 따로면 `?authSource=admin`을 붙인다
- 회사 DB에 이미 `blog_it`이라는 이름이 쓰이고 있지 않은지 확인한다. 같은 이름이 있으면
  검증기를 덮어쓴다 — 다른 이름(예: `/blogit_prod`)으로 두는 편이 안전하다

## 6. 백엔드 실행

먼저 콘솔에서 띄워 눈으로 확인한다. 상시 구동은 9단계에서 붙인다.

```powershell
python apps/api/scripts/serve.py
```

이 한 줄이 아래 긴 명령과 같다(2026-08-18에 줄였다). **포트는 `.env`의 `PORT`
한 곳에서 읽는다** — uvicorn `--port`와 `.env`의 `PORT`가 어긋나던 사고가 원천적으로
없어진다.

```powershell
# serve.py가 대신 실행해 주는 원래 명령 (직접 칠 일 없음)
python -m uvicorn app.main:app --host 127.0.0.1 --port <PORT> --app-dir apps/api
```

`--host 127.0.0.1`로 묶는 이유는 외부에서 백엔드 포트로 직접 들어오지 못하게 하기
위해서다. 외부 노출은 Nginx만 담당한다. (`--reload`는 쓰지 않는다. 운영에서 필요
없고, Chrome 프로필 파일이 바뀔 때마다 예약 발행이 도는 서버가 재시작된다.)

기동 로그에서 확인할 것:

- `저장소: ...` — MongoDB에 붙었는지. 인메모리면 `.env`가 잘못됐다
- `기능별 사용 모델:` — 각 모듈이 어떤 provider로 잡혔는지

## 7. 서버 안에서 동작 확인

```powershell
# API
Invoke-RestMethod http://localhost:8001/health

# 화면 (200과 HTML이 나와야 한다)
(Invoke-WebRequest http://localhost:8001/).StatusCode
```

`/health`의 `storageStatus`가 MongoDB를 가리키는지 본다. 그다음 브라우저로
`http://localhost:8001`에 접속해 가입 → 로그인 → 글 한 편 생성까지 확인한다.
(원고 생성은 실측 약 7분이고 이미지 생성까지 포함한다. AI 키가 실제로 도는지는 이걸로만
확인된다.)

## 8. 네이버·스레드 발행 확인

**지금 PC에 저장된 로그인 정보는 서버로 복사해도 풀리지 않는다.** 사용자 범위 DPAPI로
암호화돼 있어서, 암호화한 Windows 계정과 PC를 벗어나면 복호화되지 않는 것이 정상이다.

서버에서 새로 연결한다.

1. 발행에 쓸 Windows 계정으로 로그인한다
2. 브라우저에서 Blog-it 설정 → 네이버 계정 / 스레드 계정을 저장한다
3. 시험용 비공개 글로 발행해 본다 — 캡차·2단계 인증이 뜨면 **사람이 처리한다**

키를 함께 옮겨 자격증명을 이관하려면 [보안 배포 문서](Windows-Server-보안-배포.md)의
`POSTING_CREDENTIALS_KEY` 절차를 따른다.

## 9. 상시 구동

발행 기능을 쓴다면 **Windows 서비스로 등록하면 안 된다.** 서비스는 Session 0에서 돌아
GUI가 없고, 네이버 발행은 보이는 Chrome 창을 조작한다.

**작업 스케줄러**로 등록한다.

- 트리거: **로그온 시**
- 보안 옵션: **사용자가 로그온한 경우에만 실행** (＝ "사용자 로그온 여부에 관계없이 실행"을
  고르면 안 된다)
- 동작: `C:\apps\Blog-it\.venv\Scripts\python.exe`
  인수: `apps\api\scripts\serve.py`
  시작 위치: `C:\apps\Blog-it`
  (포트는 `.env`의 `PORT`를 따른다 — 인수에 포트를 적지 않는다)

발행을 쓰지 않는다면 NSSM 같은 서비스 래퍼도 괜찮다.

**RDP를 끊을 때 주의한다.** 연결을 끊어도(로그오프 아님) 세션은 남지만 데스크톱이 잠기며,
잠긴 세션에서 Chrome 자동화가 실패할 수 있다. 서버를 재부팅하고 RDP를 끊은 상태에서
예약 발행이 실제로 나가는지 반드시 한 번 확인한다.

## 10. Nginx 연결 — 마지막 한 번

**먼저 기존 `location /`이 무엇을 서빙하는지 확인한다.** 8888에 이미 다른 서비스가 붙어
있다면 루트 경로를 가져오는 순간 그쪽이 죽는다. 비어 있는 것을 확인한 뒤에만 아래를 넣는다.

```nginx
location / {
    proxy_pass http://127.0.0.1:8001;
    proxy_http_version 1.1;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # 요청 본문 상한이 서버에서 16MB다(참고 자료 파일 업로드).
    client_max_body_size 16m;

    # 자료 수집이 1~2분 걸린다. 기본 60초면 중간에 끊긴다.
    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
}
```

라이브 뷰(발행 크롬 화면 중계, `/live/...`)는 SSE 스트림이다. 서버가 응답에
`X-Accel-Buffering: no`를 실어 보내므로 별도 설정 없이 동작해야 하지만, **화면
프레임이 뭉쳐서 늦게 온다면** 아래를 추가한다(자세한 배경은
docs/서버-발행-개선-계획.md):

```nginx
location /live/ {
    proxy_pass http://127.0.0.1:8001;
    proxy_http_version 1.1;
    proxy_buffering off;          # SSE는 버퍼링하면 안 된다
    proxy_read_timeout 300s;      # 서버가 15초마다 keepalive를 보낸다
}
```

```powershell
nginx -t          # 문법 확인 먼저
nginx -s reload
```

그다음 `http://<회사 고정 IP>:8888` 로 외부에서 접속해 화면과 로그인을 확인한다.

## 확정 배포 순서

이 순서에서 벗어나지 않고 하나씩 진행한다.

```text
 1. Node · Python · Git · MongoDB 확인
 2. git clone
 3. 저장소 루트에서 npm ci
 4. 저장소 루트에서 npm run build
 5. Python venv 생성
 6. pip install -r apps/api/requirements.txt
 7. .env 작성                              ← PORT=8001 필수
 8. init_mongo.py 실행
 9. FastAPI를 127.0.0.1:8001로 실행
10. localhost:8001 에서 화면 · API · 글 생성 확인
11. 네이버 · Threads 서버 계정 재로그인 후 실제 발행 및 이미지 포함 확인
12. 작업 스케줄러 등록                      ← 사용자가 로그온한 경우에만 실행
13. RDP를 끊은 뒤에도 예약 · 발행 정상인지 확인
14. 기존 Nginx location / 재확인
15. location / → 127.0.0.1:8001 연결
16. 회사 IP:8888 에서 외부 최종 테스트
```

## 배포 체크리스트

넘어가기 전에 반드시 확인한다. 이 둘은 빠뜨려도 **당장은 정상으로 보이다가** 나중에
발행에서 터진다.

- [ ] **`.env`의 `PORT`가 8001인가** — uvicorn `--port`만 8001로 두면 화면은 멀쩡한데
      네이버 발행 이미지 주소가 `localhost:3000`으로 나가 그림이 빠진다
- [ ] **작업 스케줄러가 "사용자가 로그온한 경우에만 실행"인가** — "로그온 여부에 관계없이
      실행"이면 Session 0에서 돌아 Chrome GUI를 조작하지 못한다
- [ ] `AUTH_TOKEN_SECRET`·`EMAIL_ENC_KEY`·`EMAIL_INDEX_KEY` 셋 다 채웠는가
- [ ] `init_mongo.py`를 **회사 DB에 붙은 상태로** 돌렸는가
- [ ] Nginx `location /`에 기존 서비스가 없는 것을 확인했는가
- [ ] RDP를 끊고 재부팅한 뒤에도 발행이 실제로 나갔는가

## 확인한 것과 확인하지 못한 것

**로컬 PC에서 실측한 것** (2026-08-13):

- `npm run build`가 `apps/web/dist`를 만든다 — 성공, 462ms
- `PORT=8001` 하나로 화면 서빙과 발행 이미지 주소가 함께 8001을 가리킨다
  (`config.web_dir()` 마운트 확인, `naver_config.api_origin=http://localhost:8001`)
- `APP_ENV=production`에서 `AUTH_TOKEN_SECRET`과 이메일 키 둘이 없으면 기동이 멈춘다.
  셋을 채우면 통과한다
- `APP_ENV=production`의 기본값: CORS 허용 목록 `[]`, 인메모리 저장 `False`
- 요청 본문 상한이 16MB다 (`routes.py`의 413 응답)

**확인하지 못한 것** — 서버가 없어 실측이 불가능했다:

- 회사 서버에서의 Nginx 프록시 동작과 기존 `location /` 충돌 여부
- RDP 연결 해제 후 Chrome 자동화가 계속 도는지
- 작업 스케줄러 등록 후 재부팅 시 자동 기동
- 서버 MongoDB 접속 문자열과 인증 방식
