# AIONA 콘텐츠 운영

Blog-it을 **AIONA 유입용 콘텐츠 엔진**으로 쓰는 방법. 2026-08-19 작업분.

이 문서 하나면 다음 사람이 이어받을 수 있게 쓴다 — 왜 이렇게 정했는지, 무엇을 지켜야
하는지, 어디를 고치면 되는지.

---

## 1. 무엇을 만들려는가

**검색해서 들어온 사람이 원한 답을 먼저 주고, 그 과정에서 AIONA를 발견하게 하는 글.**

그 반대가 아니다. AIONA를 소개하는 글을 쓰고 트렌드를 미끼로 쓰면, 검색으로 들어온
사람은 광고를 읽은 것이 되고 바로 나간다. 유입이 목적인데 유입을 막는 셈이다.

### 독자

| | 누구인가 | 이 사람에게 필요한 것 |
| --- | --- | --- |
| **1차** | AIONA를 **모르는** 상태로 트렌드 키워드를 검색해 들어온 사람 | 검색한 그 질문에 대한 답. 그리고 "이런 도구가 있었네"라는 발견 |
| **2차** | 이미 AIONA를 쓰는 사람 | 이렇게도 쓸 수 있구나 하는 활용 사례 |

1차를 놓치면 이 블로그를 운영할 이유가 없다. 그래서 **제목에 AIONA를 넣지 않는다** —
브랜드 이름이 든 제목은 그 브랜드를 이미 아는 사람만 누른다.

### 분량 — 트렌드 70 : AIONA 활용 20 : 정리 10

글자 수를 세라는 뜻이 아니라 **어디에 무엇을 쓰는가**의 배분이다.

| 자리 | 비중 | 무엇을 쓰나 |
| --- | --- | --- |
| 도입 | 5~10% | 독자가 검색해서 들어온 그 궁금증. **AIONA는 나오지 않는다** |
| 소재·트렌드 본론 | 60~70% | 독자가 실제로 알고 싶어 한 것. 글의 몸통 |
| AIONA를 쓴 장면 | 15~20% | 왜 필요했는지 → 어떤 기능을 썼는지 → 무엇을 넣었는지 → 무엇을 얻었는지 |
| 정리·결론 | 10% | 확인한 것의 요약과, 이런 사람에게 쓸모 있겠다는 마무리 |

**예 — 소재 '빼빼로 신제품'**

```
빼빼로 신제품이 나왔다 → 맛·성분·칼로리 → 다이어트 중이라 성분이 궁금해짐
  → AIONA 자료 조사로 확인 → 실제로 확인한 내용 → 이런 걸 찾아볼 때 편하겠다
```

이 순서가 뒤집혀 "AIONA로 빼빼로 성분을 알아봤어요"로 시작하면 실패다.

### 말투 — 권유가 아니라 발견담

비중을 지켜도 문장이 "써 보세요"면 결국 광고다. 브랜드 자리에 20%를 주고 그 안을
"지금 바로 사용해 보세요"로 채워도 비중은 지켜지기 때문이다.

이 글이 서 있는 자리는 하나다:

> **이걸 알아보다가 마침 이런 기능이 있길래 한번 써 봤고, 이런 점이 도움이 됐다.**

그래서 브랜드 문단은 이 흐름을 탄다:

```
이걸 알아보고 싶었다 → 이런 점이 번거로웠다/궁금했다
  → 마침 이런 기능이 있길래 써 봤다 → 이런 결과가 나왔다 → 이런 점이 편했다
```

| 쓰지 않는 말 | 대신 |
| --- | --- |
| 지금 바로 사용해 보세요 | (권유 자체를 하지 않는다) |
| 강력 추천합니다 | 이런 걸 자주 찾아본다면 손이 덜 가겠다 |
| 꼭 한번 써 보세요 / 놓치지 마세요 | 이번에는 이렇게 확인해 봤다 |
| 무료로 시작하세요 / 요금제·혜택 안내 | (적을 이유가 없다) |

**좋았던 점만 나열하지 않는다.** 아쉬웠던 점이나 "이건 직접 확인해야 한다"는 단서가 한
줄 있으면 나머지 문장이 믿을 만해진다. 없는 단점을 지어내라는 뜻은 아니다.

마지막 문단도 권하는 말이 아니라 **겪은 것**으로 닫는다. 프롬프트가 같은 것을 지시하고,
최종 검수가 권유 문장을 `tone`으로 잡아 고친다.

### 글 맨 끝의 안내 블록

본문에서 권유하지 않는 대신, **글의 맨 끝에 고정된 한 자리**가 붙는다.

```
─────────
      (마스코트 이미지)
가입은 무료, 웰컴 크레딧 100 지급, 카드 등록 없음.
👉 aiona.kr
```

**모델이 쓰지 않는다. 코드가 붙인다.** 이유가 둘이다.

1. 매번 똑같아야 하는 **사실**이다. 모델에게 맡기면 회차마다 문구가 흔들리고 크레딧
   수·가입 조건이 슬쩍 바뀐다("웰컴 크레딧 200" 같은 것이 나온다).
2. 붙는 자리가 **최종 검수 뒤**다. 검수 앞에 두면 검수가 이 블록을 광고 문구로 읽고
   지적하거나 고친다 — 본문에 권유를 금지해 두었기 때문에 더욱 그렇다.

문구는 브랜드 자료의 「글 마지막에 붙일 안내」에서 고친다. 글을 저장할 때 그 시점의
문구가 글에 베껴지므로, 나중에 자료를 고쳐도 **이미 나간 글의 마무리는 바뀌지 않는다.**

본문은 이 블록이 뒤에 붙는다는 것을 알고 쓴다 — 그래서 본문에서 주소를 적거나 가입
안내 문단을 따로 쓰지 않는다.

## 2. 브랜드 자료

### AIONA는 처음부터 들어 있다

**등록할 것이 없습니다.** 서버를 새로 세우거나 계정을 새로 만들어도 브랜드 고르기 칸에
AIONA가 이미 있습니다 — 브랜드 목록을 처음 열 때 서버가 만들어 둡니다
(`BrandService.ensure_default_brands`).

들어 있는 것: 브랜드 소개 · 핵심 기능·서비스 · **기준표 28줄** · 주요 고객 · 공식 주소 ·
글 마지막 안내. 내용은 전부 AIONA 자료에서 옮긴 것입니다(`AIONA_브랜드_소개.txt`,
`AIONA_핵심기능_및_서비스.txt`, `AIONA_기능정리.md`) — 지어낸 문장이 없습니다.

| 하고 싶은 것 | 어떻게 |
| --- | --- |
| 마스코트·서비스 화면 이미지 올리기 | 새 글 작성 → 소재 단계 → `브랜드 관리` |
| 소개·기능·기준표 고치기 | 같은 화면에서 고치면 그대로 남습니다 |
| 코드의 최신 정의로 되돌리기 | `python apps/api/scripts/seed_aiona_brand.py --email 계정 --apply` |

**한 번 만들어진 뒤에는 코드가 덮어쓰지 않습니다.** 조회할 때마다 원래 값으로 되돌리면
올려 둔 이미지가 매번 사라지기 때문입니다. 되돌리는 것은 위 스크립트로, 사람이 눈으로
확인하고 합니다(`--apply` 없이 돌리면 무엇이 들어갈지 보여 주기만 합니다).

기본 브랜드는 **삭제되지 않습니다**. 지워도 다음 조회에서 되살아나므로, 조용히
돌아오는 대신 지울 수 없다고 알려 줍니다. 쓰지 않으려면 글을 쓸 때 고르지 않으면 됩니다.

### 마스코트 이미지 올리기

글 마지막 안내에 마스코트를 함께 붙이려면:

1. 브랜드 자료 편집 → 이미지 올리기
2. 그 이미지의 **설명(캡션)**을 `AIONA 마스코트`로 적습니다
3. 「글 마지막에 붙일 안내」의 `함께 붙일 이미지 이름`이 같은 글자인지 확인

이름이 맞는 이미지가 없으면 글자만 붙습니다 — 글이 깨지지 않습니다.

### 기준표 — "이런 상황이면 이 기능"

이 저장소에서 가장 중요한 자료입니다. 소재가 '빼빼로'인 글에서 모델이 알아야 하는 것은
"AIONA가 무엇을 하는가"가 아니라 **"이 상황에서 쓸 기능이 무엇인가"**입니다.

기능 이름은 **AIONA 화면에 실제로 있는 이름**입니다. 28줄이 들어 있고, 대표적인 것만
옮기면:

| 독자가 처한 상황 | 쓸 기능 |
| --- | --- |
| 어떤 정보를 알아보고 싶을 때 | 자료 조사 |
| 여러 자료를 교차 확인해 근거를 갖춰야 할 때 | 심층 리서치 |
| 긴 자료·뉴스·문서를 빨리 파악해야 할 때 | 문서 요약 |
| 유튜브 영상이나 웹 기사를 요약해야 할 때 | AI 요약 |
| 해외 자료를 확인해야 할 때 | 번역 |
| 회사에 보낼 글을 써야 할 때 | 이메일·메시지 작성 |
| 회의나 발표를 준비할 때 | 회의 준비 |
| 후기나 답글을 써야 할 때 | 리뷰 답글·후기 쓰기 |
| 한 주 먹을 것을 미리 정해야 할 때 | 주간 식단 짜기 |
| 아이 학교·가정 알림을 정리할 때 | 알림장 정리 |
| 명절·행사·경조사 문구가 필요할 때 | 경조사 문구 |
| 계약서나 약관을 확인해야 할 때 | 계약서·약관 핵심 짚기 |
| 의심스러운 문자를 받았을 때 | 사기 문자 확인 |
| 블로그·SNS에 쓸 이미지가 필요할 때 | 이미지 생성 |
| 시험·과제를 준비할 때 | 학습 코치 |

전체는 `apps/api/app/modules/brand/defaults.py`에 있고, 화면에서도 고칠 수 있습니다
(브랜드 자료 편집 → "이런 상황이면 이 기능"). 줄마다 상황·기능·닿는 소재 세 칸입니다.

이 표가 두 곳에서 쓰입니다.

1. **원고 프롬프트** — 소재에 닿은 줄만 골라 실어서, 모델이 실제로 있는 기능 이름을
   쓰게 합니다. 표가 비면 모델이 줄글에서 기능을 짐작하거나 없는 이름을 지어냅니다.
2. **결합 가능성 판정(A·B·C)** — 지금 소재가 AIONA와 자연스럽게 닿는지를 이 표로 잽니다.

**검색어 적는 법.** 여러 낱말로 적으면 **그 낱말이 다 있을 때만** 닿습니다. `학교 준비물`은
'학교 준비물 목록'에 닿고 '일본 여행 준비물'에는 닿지 않습니다. 넓게 닿게 하려면 짧게
적습니다. `정보`·`사용`·`방법`처럼 어디에나 있는 낱말은 판정에서 걸러지므로 넣어도 소용없습니다.

## 3. 글 한 편 만들기

### 화면에서

1. 새 글 작성 → **소재**에 트렌드 키워드를 적는다.
2. **활용할 브랜드·서비스**에서 AIONA를 고른다.
3. 역할을 고른다 — 기본값은 `활용한 도구로`다.
4. 그 아래에 **결합 가능성**이 뜬다. 등급을 보고 계속할지 정한다.
5. 목적·연령·카테고리를 채우고 저장 → 나머지는 평소와 같다.

AIONA 앱스튜디오에서 들어오면 2번이 이미 되어 있다(아래 5장).

### 결합 가능성 — A·B·C

| 등급 | 뜻 | 어떻게 하나 |
| --- | --- | --- |
| **A** 바로 연결 | 소재가 기준표의 상황과 곧바로 닿는다 | 적극적으로 쓴다 |
| **B** 상황 필요 | 소재를 다루다 보면 그 상황이 생긴다 | 쓴다. 도구를 꺼내기 전에 필요해지는 장면을 먼저 만든다 |
| **C** 억지 연결 | 닿는 곳이 없다 | **쓰지 않는다** |

C를 버리는 것이 중요하다. 언급 수를 늘리려고 모든 트렌드에 AIONA를 넣으면 결국 광고성
문장만 쌓이고, 블로그 전체가 홍보 채널로 읽힌다.

화면은 C에서 저장을 **한 번** 막는다. 다시 누르면 그대로 저장된다 — 판정은 기준표로
재는 것이라 표에 아직 없는 상황도 C로 나오기 때문이다. 그때 할 일은 둘 중 하나다:
**기준표에 그 상황을 더하거나**, 그 소재를 버리거나.

### 글의 유형 네 가지

한 가지 형태로만 만들면 금방 비슷해진다. 큐를 짤 때 섞는다.

| 유형 | 모양 |
| --- | --- |
| **A 직접 사용 후기** | 요즘 ○○가 화제라 직접 알아보다가 자료 조사 기능을 썼다 |
| **B 문제 해결** | ○○ 때문에 궁금한 것이 생겨 ○○ 기능으로 정리했다 |
| **C 비교·검증** | 인터넷에서 말이 다른 내용을 자료를 찾아 비교했다 |
| **D 일상 활용** | 일상에서 생긴 작은 일을 ○○ 기능으로 해결했다 |

넷 다 **"알아보다가 써 봤다"**의 변주다. 어느 것을 골라도 권하는 글이 되어서는 안 된다.

**단, 실제로 하지 않은 행동을 "제가 직접 사용해봤는데"라고 만들어 내면 안 된다.**
실제 AIONA 결과를 참고자료로 넣었을 때만 후기 형태로 쓴다. 넣지 않았으면 "이 기능을
활용하면…" 형태가 된다. 프롬프트도 같은 것을 지시하고, 최종 검수가 위반을
`unsupported`로 잡는다.

## 4. 운영 규칙

이어받는 사람이 이것만 지키면 방향이 크게 변하지 않는다.

1. 최신 트렌드를 고른다.
2. AIONA 기능과 연결 가능성을 판단한다(A·B·C).
3. 자연스럽게 연결 가능한 경우만 작성한다 — **C는 버린다**.
4. 글 비중은 트렌드 70 / AIONA 활용 20 / 결론 10을 기준으로 한다.
5. AIONA 기능명은 **기준표에 실제로 있는 것만** 쓴다.
6. 실제 사용 결과가 없으면 사용 후기처럼 쓰지 않는다.
7. AIONA 설명보다 **독자가 검색한 질문에 먼저 답한다**.
8. 마지막에만 자연스럽게 AIONA로 연결하되, **권유가 아니라 겪은 것**으로 닫는다.
9. 좋았던 점 옆에 한계를 한 줄 붙인다. 장점만 있는 문단은 광고로 읽힌다.

### 첫 운영 큐

처음부터 수십 개를 걸지 말고, 최신순 트렌드에서 6~10개를 고른다. 유형과 기능을 섞는다.

**거는 방법은 둘이다.**

| 어디서 | 어떻게 | 언제 쓰나 |
| --- | --- | --- |
| **자동 포스팅** 탭 | 소재를 줄마다 적고, 아래 `활용할 브랜드 · 서비스`에서 AIONA를 한 번 고른다(배치 전체에 하나) | 6~10편을 한 번에 걸 때 |
| **새 글 작성** + 예약 발행 | 소재·브랜드·역할을 글마다 고르고 작업 시각을 정한다 | 제목·방향까지 직접 정하고 싶을 때 |

자동 포스팅으로 건 글도 **화면으로 만든 글과 같은 처리**를 받는다 — 브랜드 자료가
얹히고, 역할이 활용(UTILITY)으로 잡히고, 결합 가능성이 재어진다(둘 다
`with_brand_materials` 한 함수를 거친다). 다만 이 탭은 소재가 반드시 있는 흐름이라
역할을 고르는 칸이 없다: 브랜드는 언제나 활용한 도구다.

결합 가능성 경고는 자동 포스팅 탭에 없다. 줄마다 판정을 띄우면 그 화면이 하려는
"적어 두고 손대지 않는다"와 어긋나기 때문이다 — 대신 억지 조합으로 걸리면 원고가
브랜드를 마지막에 한 번만 짧게 언급한다. 미리 확인하고 싶으면 새 글 작성에서 소재를
한 번 넣어 등급을 보면 된다.

| 갈래 | 쓸 기능 |
| --- | --- |
| 음식 트렌드 | 자료 조사 |
| 다이어트 | 자료 조사 |
| 신제품 | 자료 조사 / 리뷰 답글·후기 쓰기 |
| 해외 이슈 | 번역 |
| 업무 트렌드 | 회의 준비 |
| 취업·직장 | 이메일·메시지 작성 |
| 식단 | 주간 식단 짜기 |
| 명절·행사 | 경조사 문구 |

같은 형식으로 몰아서 발행하지 않는다.

## 5. AIONA 앱스튜디오에서 들어오기

앱스튜디오 카드에서 이 주소를 연다:

```
https://<Blog-it 주소>/?campaign=aiona#/write
https://<Blog-it 주소>/#/write?campaign=aiona     (둘 다 됩니다)
```

**하는 일은 하나뿐이다: 이름이 AIONA인 브랜드를 미리 골라 준다.** 로그인·계정 연동은
하지 않는다 — 주소는 누구나 적을 수 있어서 그 이상의 신뢰를 줄 수 없고, 브랜드 자료는
어차피 로그인한 사용자 자기 것 안에서만 찾는다.

저장된 글을 다시 열 때는 적용되지 않는다. 브랜드를 일부러 뺀 글을 다시 열었을 때 그
브랜드가 되붙으면 안 되기 때문이다.

앱스튜디오 카드 문구는 이 정도면 충분하다:

> **블로그 트렌드 포스팅**
> 실시간 트렌드를 찾아 자료 조사부터 원고 생성, 이미지 제작, 블로그 발행까지 한 번에.

SSO·계정 통합은 하지 않았다. 먼저 필요한 것은 사람들이 앱스튜디오에서 클릭해 Blog-it
까지 들어와 글을 만드는 흐름이고, 그것은 위 한 줄로 완성된다.

## 6. 발행 전 확인

실제로 끝까지 돌려 보고(트렌드 선택 → AIONA 선택 → 제목 → 자료 검증 → 원고 → 이미지 →
네이버 발행) 아래를 본다. 최소 3~5건.

- [ ] 트렌드가 글의 중심인가 — 도입부와 첫 섹션에 AIONA가 나오지 않는가
- [ ] 제목에 AIONA·기능 이름이 없는가
- [ ] 나온 기능 이름이 **기준표에 있는 것**인가 (없는 이름을 지어내지 않았는가)
- [ ] 확인하지 않은 사용 결과를 "직접 써 봤더니"로 쓰지 않았는가
- [ ] **권유 문장이 없는가** — "써 보세요", "추천합니다", 가입·요금제 안내
- [ ] 좋았던 점 옆에 한계가 한 줄 있는가
- [ ] 제목이 광고처럼 보이지 않는가
- [ ] 이미지가 주제와 맞는가
- [ ] 출처가 정상인가
- [ ] 네이버 자동 발행이 정상인가
- [ ] 앱스튜디오에서 들어왔을 때 AIONA가 미리 골라져 있는가
- [ ] 글 맨 끝에 안내 블록(사실 한 줄 + 👉 aiona.kr)이 **한 번만** 붙었는가
- [ ] 본문 안에 주소나 가입 안내 문단이 따로 들어가지 않았는가

읽고 나서 "AIONA 홍보글"이 아니라 **"트렌드 글을 읽다가 AIONA라는 도구를 발견했다"**는
느낌이면 성공이다.

## 7. 블로그 대문과 썸네일

| 파일 | 크기 | 쓰는 곳 |
| --- | --- | --- |
| [`assets/aiona-blog-cover.svg`](assets/aiona-blog-cover.svg) | 966 × 600 | 네이버 블로그 PC 대문 |
| [`assets/aiona-post-thumbnail.svg`](assets/aiona-post-thumbnail.svg) | 800 × 800 | 게시물별 대표 이미지 템플릿 |

PNG로 바꿔 올린다:

```bash
npx @resvg/resvg-js-cli docs/assets/aiona-blog-cover.svg cover.png
npx @resvg/resvg-js-cli docs/assets/aiona-post-thumbnail.svg thumb.png
```

**대문은 하나만 둔다.** 업종별로 여러 개 만들지 않는다 — AIONA 블로그 자체가 하나의
브랜드 블로그라, 방문자가 어느 것이 이 블로그인지 알 수 있어야 한다. 글마다 달라져야
하는 것은 대문이 아니라 썸네일이다.

대문이 노리는 감정은 **소개받음 → 이해함 → 나도 한번 써 보고 싶음**이다. "이게 뭐지?"가
먼저 오면 실패라, 첫 화면에 추상적인 문구 대신 **실제로 꺼내 쓸 수 있는 작업들**을
늘어놓는다. 로봇·뇌 이미지를 쓰지 않은 것도 같은 이유다 — "AI 일반"을 그리면 무엇을 하는
서비스인지가 사라진다.

썸네일에서 고칠 곳은 두 군데다(파일 안에 `data-slot`으로 표시해 뒀다).

| 자리 | 무엇을 |
| --- | --- |
| `headline` | 글 제목. 두 줄까지 — 세 줄이 되면 글자를 줄인다 |
| `feature` | 이 글에서 **실제로 쓴** 기능 이름. 쓰지 않았으면 그 그룹을 통째로 지운다 |

카드·썸네일의 기능 이름은 **기준표의 이름과 같아야 한다**. 대문의 기능명과 글에 나오는
기능명이 다르면 같은 서비스로 읽히지 않는다.

실제 로고 파일이 생기면 대문 SVG의 워드마크 그룹(`AIONA` 텍스트 + 노란 밑줄)을 그것으로
바꾼다.

## 9. 하지 않은 것

| 무엇 | 왜 |
| --- | --- |
| SSO·계정 통합 | 앱스튜디오 → Blog-it 진입 흐름이 먼저다. 진입값 한 줄로 충분히 자연스럽다 |
| 업종별 블로그 대문 여러 개 | AIONA 블로그 자체가 하나의 브랜드 블로그다. 대표 대문 1개 + 게시물별 썸네일 템플릿이 낫다 |
| C 등급 완전 차단 | 판정은 기준표로 재는 것이라 표에 없는 상황도 C가 된다. 끝까지 막으면 그 판단을 뒤집을 방법이 없어진다 — 한 번 막고, 다시 누르면 통과시킨다 |
| 트렌드 수집 단계의 A·B·C 표시 | 판정은 소재를 확정한 뒤라야 뜻이 있다. 트렌드 카드마다 등급을 붙이면 아직 소재가 없는 상태에서 재는 셈이다 |
