## 왜 이렇게 지었나

코드는 무엇을 하는지만 말합니다. 왜 그렇게 했는지는 여기 적습니다.

- **Python/FastAPI + React.** 처음에는 Node/TypeScript로 시작했고, 타입을 프론트와
  공유하려는 이유였습니다. 팀 아키텍처 문서가 전제하던 스택으로 되돌렸습니다(`9d99b24`).
  대신 **타입 공유는 포기**했습니다 — 백엔드 모델(Pydantic)과 프론트 타입(`api/types.ts`)은
  손으로 맞춥니다. 어긋나면 빌드가 아니라 런타임에 드러납니다. 알고 치른 값입니다.

- **MongoDB.** `blogTask` 문서 하나가 글 한 편의 전 과정을 담습니다. 상태 전이는
  `{postId, version}` 조건부 갱신으로 원자적으로 처리합니다. 두 탭에서 같은 글을 만지면
  나중 것이 409로 거절됩니다.

- **큐 미들웨어는 없습니다.** 오래 걸리는 작업(M3 검증, M4 원고)은 FastAPI 백그라운드
  작업으로 돌리고 화면이 진행 상황을 물어봅니다. 작업 상태는 큐가 아니라 **MongoDB의
  blogTask 문서**에 있습니다 — `status`가 대기·처리·완료·실패를, `progress`가 현재 단계를
  담고, `postId`가 곧 작업 식별자입니다. 생성 **도중** 프로세스가 죽으면 시작할 때
  `recover_interrupted_jobs`가 한 번 훑어 되살립니다. **살아 있는 임차가 없는 것만**
  손댑니다 — 서버를 여러 대로 돌릴 때, 한 대가 재시작한다고 다른 대가 지금 돌리고 있는
  작업을 실패로 만들면 안 되기 때문입니다.

- **예약 워커도 새 인프라를 들이지 않았습니다.** Celery를 붙이는 대신 FastAPI가 이미
  돌리는 asyncio 루프에 백그라운드 태스크 하나를 띄우고, 위와 같은 임차로 프로세스 간
  중복을 막습니다(`blogit:scheduled:{batchId}`). 예약 상태도 큐가 아니라 MongoDB의
  `scheduled_batches`·`scheduled_jobs` 문서에 있어서, 재시작해도 남은 작업이 이어집니다.

- **예약 포스팅은 오케스트레이션 한 겹입니다.** 예약용 생성기를 따로 만들면 프롬프트가
  둘이 되고, 한쪽만 고쳐지는 순간 "같은 앱인데 예약으로 나간 글만 품질이 다르다"가
  됩니다. 그래서 `scheduled_posting`은 어느 서비스를 언제 부르는지만 알고, 원고·이미지에
  관한 결정은 하나도 갖지 않습니다.

- **Redis는 프로세스 바깥에 두어야 하는 상태를 담습니다.** 트렌드 키워드 캐시, **트렌드
  노출 이력**, **잡 임차**(글 생성·예약 배치) 세 가지입니다. 프로세스 메모리에 두면 서버를
  껐다 켤 때 사라지고, API 서버를 두 대 이상으로 늘리면 서버마다 다른 것을 봅니다 —
  한쪽에서 본 키워드가 다른 쪽에서 또 뜨고, 같은 예약 배치를 두 서버가 동시에 돌립니다.
  `REDIS_URL`이 없으면 디스크·메모리로 물러나고(로컬 개발), 그 사실이 시작 로그와
  `GET /health`의 `sharedStateStatus`에 찍힙니다. 운영에서는 반드시 설정합니다.

- **LLM은 별도 프로세스가 아닙니다.** `app/llm/`을 API가 같은 프로세스에서 import합니다.

- **목업이 없습니다.** 키가 없으면 API는 시작을 거부합니다. 그럴듯한 가짜 원고를 내주는
  것보다 안 뜨는 게 낫습니다. 역할별 모델 배정은 `app/llm/provider_config.py`의
  `ROLE_SPECS`가 전부입니다.

- **오래 걸리는 것은 미리 시작합니다.** 사용자가 다음 화면에 도착하기를 기다리지 않고,
  필요한 입력이 갖춰진 순간 백그라운드로 띄웁니다. 두 자리가 그렇습니다 — 소재를 저장하면
  제목 키워드를(`TrendService.start_keyword_prefetch`), 방향을 고르면 콘텐츠 설계를
  (`DraftService.start_content_plan_prefetch`) 미리 만듭니다. **화면의 요청은 돌고 있는
  선행분에 붙습니다** — 붙지 않으면 같은 일이 두 번 돌아 비용이 두 배가 됩니다.
  타이핑 도중에 추측으로 돌리지는 않습니다: 소재를 고칠 때마다 다시 돌고, 소재 관련순은
  LLM 관련도 판정을 쓰므로 그만큼 그대로 비용입니다.

- **프롬프트는 코드에 있습니다.** 파일로 빼는 방법도 시도했지만 아무도 읽지 않아 지웠습니다.
  프롬프트가 조용히 바뀌는 것은 `tests/test_prompt_parity.py`가 막습니다 — 실제로 나가는
  요청 본문을 고정 fixture와 바이트 단위로 비교합니다.

- **네이버 발행은 브라우저 자동화입니다.** 네이버가 2020년에 블로그 글쓰기 API를 닫아서,
  Selenium으로 로컬 Chrome의 스마트에디터를 조작합니다(`app/posting/naver/`). 캡차나 2단계
  인증은 자동으로 넘기지 않고 사람에게 넘깁니다 — 그 검사는 프로그램을 막으라고 있는
  것이고, 이 코드가 그것과 싸우지는 않습니다.

- **네이버 비밀번호는 DB에 넣지 않습니다.** 공용 Atlas에 들어간 비밀번호는 컬렉션을 읽을 수
  있는 사람 누구의 것이기도 합니다. 이 PC에서 Blog-it 로그인 사용자별로 분리하고, Windows
  DPAPI로 이 Windows 계정에 묶어 암호화합니다(`app/posting/credentials.py`).

## 데이터가 어디에 남나

| 무엇 | 어디에 | 사라지는 때 |
|---|---|---|
| 계정 (이메일, 비밀번호 **해시**) | MongoDB `users` — `scrypt$<salt>$<key>` | 지울 때까지 |
| 페르소나 선택 카탈로그 (`p_1`~`p_9` + `custom`) | 백엔드 `modules/persona/catalog.py` → `GET /personas` | 배포된 카탈로그가 바뀔 때 |
| 공용 페르소나 프리셋 (`p_1`~`p_9`) | MongoDB `persona` — 백엔드 카탈로그를 시작 시 upsert | 직접 삭제할 때까지 (현재 카탈로그 항목은 시작 시 갱신) |
| 사용자 설정 (선택한 페르소나 ID, 커스텀 프롬프트, 해시태그 수, 자동 발행) | MongoDB `userSettings` | 지울 때까지 |
| 글 한 편의 전 과정 (입력·트렌드·검증·원고·이미지·발행 로그) | MongoDB `blogTask` 문서 하나 | 지울 때까지 |
| 트렌드 키워드 풀 (공용·최신순) | MongoDB `trend_keywords` — 키워드당 문서 하나(`key1…` + source·at·score·seq), 영구 누적 | 지울 때까지 (소스당 200개 상한, 오래된 것부터 정리) |
| 소재별 관련 키워드 + 관련도 판정 | MongoDB `material_related_keywords` — (소재 키, 정규화 키워드)당 문서 하나 | 지울 때까지 (소재당 120개 상한, 관련도 낮은 것부터 버림) |
| 예약 배치 (방식·간격·글의 개수·진행 로그) | MongoDB `scheduled_batches` — 로그는 최근 200줄 | '새 예약 시작'으로 버리거나 지울 때까지 |
| 예약 작업 (소재 하나 = 문서 하나, 연결된 postId·상태) | MongoDB `scheduled_jobs` | 작업을 빼거나 배치를 버릴 때 |
| 트렌드 풀 폴백 캐시 | 저장소 루트 `.trend-cache` (gitignore) — **Mongo에 붙지 못했을 때만** | 폴더를 지우면 다음 조회 때 다시 수집 |
| 잡 임차(같은 작업의 중복 실행 방지) | `REDIS_URL`이 있으면 Redis, 없으면 저장소 루트 `.job-leases` (gitignore) | 임차 기간이 지나면 자동 만료 |
| 로그인 토큰 | 브라우저 localStorage `blog-it:session` | 만료 시각이 지나면 다음 로드에서 버립니다 |
| 공용 페르소나 목록 캐시 | 브라우저 localStorage `blog-it:persona-catalog` | 다음 `GET /personas` 성공 시 갱신 |
| 온보딩 안내를 봤는지 | 브라우저 localStorage `blog-it:writing-setup-onboarding-seen:<userId>` | 브라우저 데이터를 지울 때까지 |
| **네이버 세션 쿠키** | 이 PC의 `.naver-profile-users/<userId 해시>/` (gitignore) | 사용자별 폴더를 지우면 로그아웃됩니다 |
| **네이버 아이디·비밀번호** | 같은 사용자별 로컬 폴더의 `credentials.json` — Windows DPAPI로 **이 Windows 계정에만** 열리게 암호화 | 사용자별 폴더를 지우면 함께 사라집니다 |

`blogTask`는 사용자마다 컬렉션을 따로 만들지 않는 공유 컬렉션입니다. 각 문서의 필수
`userId`가 소유자를 나타내며, 목록·단건 조회·삭제는 로그인 토큰의 `userId`를 MongoDB
쿼리 조건에 포함합니다. 따라서 Atlas/Compass 컬렉션 화면에는 전체 글이 보이는 것이
정상이고, 특정 사용자의 글은 `{ "userId": "user_..." }` 필터로 확인할 수 있습니다.

**DB에 없는 것**: 네이버 비밀번호. 공용 Atlas 클러스터라, 거기 들어간 네이버 비밀번호는
그 컬렉션을 읽을 수 있는 사람 누구의 것이기도 합니다. 비밀번호를 돌려주는 API도 없습니다 —
읽히는 것은 아이디뿐입니다. Blog-it 계정 비밀번호도 원문은 저장하지 않습니다(scrypt 해시).

## 트렌드 키워드 저장·캐시

키워드 수집은 외부 API를 호출합니다(SerpApi는 검색 건당 과금). 수집분은 MongoDB
`trend_keywords` 컬렉션에 **키워드 하나당 문서 하나**(`_id: key1, key2, …` + `keyword,
source, at, score, seq`)로 **영구 누적**되고, 화면 조회는 이 저장분에서 바로 서빙합니다.
자동 재수집은 30일에 한 번뿐이며, 더 최신 키워드가 필요하면 '트렌드 새로 수집' 버튼이
소스를 즉시 다시 부릅니다(1회 호출당 소스별 20개 상한, 같은 키워드는 upsert로 시간·점수만
갱신). '다른 후보 보기'는 API를 부르지 않습니다 — 최신순에서는 저장분의 **인기순 상위
구간(상위 20%, 최소 표시 개수의 2배)에서 무작위 16개**를(중복 노출 허용), 소재 관련순에서는
아직 안 본 적격 후보를 돌려줍니다.

소재 관련 키워드는 **별도 컬렉션 `material_related_keywords`**에 담습니다. `trend_keywords`는
"지금 한국에서 뜨는 것"이라는 하나의 공용 풀인데, 소재 관련어는 성격이 정반대라서입니다 —
'배틀그라운드 감도 설정'은 배틀그라운드 글에만 의미가 있고, 최신순 패널에 섞이면 아무
관계 없는 사용자에게 노출됩니다. 문서의 키는 **소재**이지 사용자가 아니라서, 같은 소재로
쓰는 모든 사용자가 한 번 검증한 풀을 재사용합니다(수집·채점 비용이 글 수가 아니라 소재
수에 비례합니다). 관련도 판정도 이 문서에 함께 저장해, 후보가 늘어도 **새 키워드만**
채점합니다.

Mongo에 붙지 못한 경우에만 저장소 루트의 `.trend-cache` 디스크 캐시(gitignore)로 물러납니다.
`REDIS_URL`을 설정하면 디스크 대신 Redis를 씁니다(선택).

## 트렌드 점수 체계

키워드에는 성격이 다른 점수 두 종류가 있습니다.

**1. 수집 점수 `score` (DB에 저장)** — 키워드 자체의 속성.

- 소스가 주는 원시 신호(구글 검색량 버킷, 네이버 검색량 재정렬 순위, 유튜브 태그
  빈도)는 단위가 제각각이라 그대로 비교할 수 없습니다. 저장 전에 **그 소스·그 수집
  회차 안에서의 상대 인기 40~100**(min-max, 100=1위급)으로 정규화합니다
  (`aggregate._rescore_pool`).
- 정확한 검색량이 아니므로 화면에서는 '검색 관심도(추정)'로만 부릅니다.
- '최신순' 정렬이 이 값을 씁니다.

**2. 소재 관련도 채점 (LLM, `material_related_keywords`에 저장)** — 소재 관련순에서만 쓰는 키워드 × 소재 조합의 속성.

- 소재 관련순을 처음 열 때 M2 모델이 풀을 60개씩 병렬로 채점하고, 이후에는 저장된 판정을
  재사용합니다. 최신순은 이 채점을 호출하지 않아 소재가 바뀌어도 LLM을 기다리지 않습니다.
  프롬프트와 채점 체계 전체 설명: `keyword_relevance_prompt` (docstring에 정리돼 있습니다).
- 키워드마다 네 값을 냅니다 (각 0~100):
  - `relevance` 종합 — 이 소재·목적으로 글이 되는가
  - `subjectRelevance` — 소재 자체와의 직접 관련성만 (**소재 관련순의 게이트·정렬 축**)
  - `purposeRelevance` — 글 목적의 글감으로 맞는가 (툴팁 표기용)
  - `personaRelevance` — 페르소나(화자)가 자연스럽게 다룰 수 있는가 (미설정 시 100, 툴팁 표기용)
- 같은 '장마'라도 소재가 '제습기'면 높고 'AIONA'면 낮습니다 — 그래서 공용 풀
  (`trend_keywords`)이 아니라 **소재로 키를 잡은 문서**에 판정을 함께 저장합니다.
  키는 소재 표기를 정규화한 값 하나뿐이라(공백·대소문자·기호만 지웁니다), 같은 소재로
  쓰는 사람이 여럿이면 한 번 채점한 것을 모두가 씁니다.
- 새 후보가 30개 붙어도 **채점 안 된 것만** 모델에 보냅니다. 채점 기준이 바뀌면
  `RELEVANCE_PROMPT_VERSION`이 올라가고, 버전이 다른 판정은 '채점 안 된 것'으로 보아
  자연히 다시 채점됩니다(전체 삭제가 필요 없습니다).

| 보기 | 노출 조건 | 리스트 순서 | '추천' 배지 |
|---|---|---|---|
| 최신순 | 소재 메아리·저품질 제외 (LLM 채점 없음) | `score` 내림차순 (실시간 인기) | 트렌드 강도 최고점 1개 |
| 소재 관련순 | **소재 관련도 30+** (30 미만 = 채점 루브릭의 "아무 상관 없음" — `TREND_ELIGIBLE_MIN_SUBJECT`) | 통과분을 **소재 관련도** 내림차순 (동점은 `score`) | 리스트 1위 (= 관련된 것 중 관련도 최고) |

- 예전의 소재 60 AND 목적 50 AND 페르소나 40 게이트는 니치 소재에서 후보가 전멸해
  폐기했습니다. 이제 "소재와 관련된 키워드면 다 보여주되, 아무 상관 없는 것만 뺀다"가
  소재 관련순의 원칙입니다.
- 소재 관련순은 **DB 저장분을 먼저** 검사하고, 게이트를 통과한 후보가 하나도 없을 때만
  소스 API를 새로 수집해 같은 검증을 거칩니다(수집 원본을 검증 없이 노출하지 않음).
- 트렌드 강도(`trendScore`)는 인기 0.65 + 교차 확인 0.35(2개 이상 소스에서 확인되면
  100, 아니면 45) 기반의 합성값입니다. 상세 수식과 근거는
  `apps/api/app/llm/trends/aggregate.py`의 `_monthly_trend_score`·`_mode_trend_score`
  주석에 있습니다.

## 예약 포스팅 API

여기서 '예약 포스팅'은 **백엔드 모듈 이름**(`scheduled_posting`)입니다. 화면 이름과
다릅니다 — 이 API를 쓰는 탭은 「자동 포스팅」이고, 걸어 둔 것을 보는 탭은 「작업 관리」이며,
새 글 작성도 작업 시각을 적으면 같은 모듈을 지납니다(2026-08-12).

| 메서드 | 경로 |
| --- | --- |
| `POST` | `/scheduled/naver/batches` (시작) |
| `GET` | `/scheduled/naver/batches/active` · `/scheduled/naver/batches/{id}` |
| `POST` | `.../batches/{id}/pause` · `/resume` · `/stop` · `/discard` |
| `POST` | `/scheduled/naver/jobs/{id}/retry` · `/cancel` |
| `PATCH` | `/scheduled/naver/jobs/{id}` (발행 시각·플랫폼 변경) |
| `GET` | `/scheduled/naver/jobs` (배치를 넘나드는 내 예약 전부) |
| `DELETE` | `/scheduled/naver/jobs/{id}` |

모든 경로가 **로그인 토큰의 `userId`로 소유권을 검사**합니다. 클라이언트가 보낸 userId는
쓰지 않습니다 — 다른 사용자의 배치 ID를 알아도 조회·수정할 수 없습니다.

`POST /scheduled/naver/batches`의 `schedules[]` 한 줄이 글 하나입니다.

| 필드 | 뜻 |
| --- | --- |
| `topic` | 소재(필수) |
| `publishAt` | 절대 발행 시각. **줄마다 있어도 없어도 됩니다**(2026-08-12). 한 줄이라도 있으면 배치는 절대 시각 방식이고, 없는 줄은 `after_job_id`로 **앞 줄에 매달립니다** — 앞 글이 끝나면 그때가 올릴 때입니다. 전부 없으면 예전처럼 간격 방식입니다. |
| `publishNaver` · `publishThreads` | 어디에 올릴지. 둘 다 켜면 네이버가 먼저입니다. |
| `subjectCategory` | 소재 분야(선택, 2026-08-12). `SUBJECT_CATEGORIES` 안의 값만 받고, 작업에 저장돼 `create_blog_task`로 넘어갑니다. **빈 문자열은 '고르지 않음'** 으로 읽습니다. |

**섞인 배치는 입력한 줄 순서를 지킵니다.** 전부 시각을 적은 배치만 시각 순으로 다시
세웁니다 — 섞인 배치를 재정렬하면 '앞 글'이 사용자가 적은 줄과 달라집니다.

간격 규칙(`MIN_PUBLISH_GAP_SECONDS`, 12분)은 **시각을 적은 줄끼리만** 봅니다. 비운 줄은
약속한 시각이 없어 넘길 시각도 없습니다.

새 글 작성에서 건 예약은 `starts_from_prepared_post` 작업이라 이 경로를 지나지 않습니다.

예약 워커가 부르는 순서는 새 글 작성과 같습니다.

```text
create_blog_task → recommend_topics → generate_topics → select_topic
→ analyze_intent_candidates → select_intent → generate_draft → publish_blog_task
```

프롬프트·이미지 정책·발행 계획은 전부 불리는 쪽에 그대로 있습니다
(`app/modules/scheduled_posting/service.py`는 '어느 것을 언제 부르는가'만 압니다).

**알아 둘 동작**

- **발행은 언제나 하나씩** 돕니다. 같은 프로필로 크롬이 두 번 뜨면 프로필 잠금 때문에
  발행이 통째로 실패합니다.
- **원고 준비는 정한 시각 예약에 한해 동시에** 돕니다(최대 3편, 2026-08-07). 예전에는
  준비도 하나씩이었고 그 준비가 워커의 tick을 통째로 붙잡고 있었습니다. 원고 한 편이 실측
  6분 27초(중앙값)라 세 번째 글은 20분 뒤에야 시작됐고, 더 나쁘게는 **그 6분 동안 다른 글의
  발행 시각을 아무도 보지 않았습니다.** 간격 방식은 예전 그대로 하나씩입니다 — 그쪽은
  '앞 글이 발행된 뒤 N분'이 곧 순서라 미리 만들어 둘 대상이 정해지지 않습니다.
- 정한 시각 예약은 **글과 글이 최소 10분** 떨어져야 합니다(`MIN_PUBLISH_GAP_SECONDS`).
  발행이 하나씩 도는데 발행 동작 자체가 네이버 30초·스레드 2분쯤 걸려, 더 촘촘하면 뒤 글이
  반드시 자기 시각을 넘깁니다. 예약 시각은 **발행을 시작하는 시각**입니다.
- **서버를 재시작해도 이어집니다.** 시작 시 저장된 단계 표시가 아니라 연결된 BlogTask의
  **실제 상태**를 보고 복구합니다. 다만 결과가 불확실한 네이버 발행은 자동으로 다시 하지
  않습니다 — 같은 글이 두 번 올라가는 것보다 사람이 확인하는 편이 낫습니다.
- 캡차·2단계 인증이 뜨면 그 작업은 `NEEDS_HUMAN`으로 멈추고 배치가 대기합니다.
- **작업이 실패하면 다음 작업은 간격을 기다리지 않고 시작합니다**(`_fail`이 다음 실행
  시각을 정하지 않습니다). 발행까지 간 실패가 아니라면 네이버에 부담이 없어 그대로
  두었지만, 의도한 설계는 아닙니다.
- 한 소재로 여러 편을 쓸 때는 **새 프롬프트를 만들지 않고** 기존 API가 이미 받는 인자
  셋으로 각도를 벌립니다 — 변종 번호로 트렌드 키워드의 n번째를 고르고, 같은 배치의 앞선
  글이 쓴 제목을 `excludeTitles`로 빼고, `regenerationCount`에 변종 번호를 넘겨 제목
  생성기가 이번 회차의 방향을 다르게 잡도록 합니다.
